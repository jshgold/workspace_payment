# 알려진 한계 (phase-03 진행 중 정리)

phase 파일에 작업으로 잡혀 있지 않지만, 대화에서 확인된 구멍을 기록해 둔다. 지금은 의도적으로 두고 넘어간다.
phase-03 마지막 질문("PG 승인은 성공했는데 서버가 죽으면?")의 재료이기도 하다.

| # | 한계 | 현재 동작 | 영향 | 풀려면 |
|---|---|---|---|---|
| 1 | 방치된 PENDING 주문이 정리되지 않음 | 주문하기를 누르고 결제 없이 나가면 PENDING 행이 계속 쌓임. 반복하면 주문번호가 다른 행이 N개 생김 | 재고는 승인 시 차감이라 영향 없음. 데이터 증가, 반복 호출에 무방비 | 만료 배치(일정 시간 지난 PENDING → CANCELED/EXPIRED), rate limit |
| 2 | PAYING에서 영구히 남을 수 있음 | PG 타임아웃, 서버 다운, 보상 취소 실패 시 PAYING 유지 | 돈은 나갔는데 주문이 PAID가 아닐 수 있음 | 오래된 PAYING을 PG에 조회해 완료 또는 복구하는 스케줄러(결제 상태 대사) |
| 3 | 결제 조회 API 없음 | `PaymentClient`에 승인(approve), 취소(cancel)뿐 | 2번을 풀 수단이 없음 | `PaymentClient`에 결제 조회 메서드 추가 |
| 4 | 선점에 실패한 요청이 예외를 그대로 받음 | 이미 결제 중인 주문에 승인 요청이 또 오면 `IllegalStateException` | 사용자 입장에서는 같은 요청의 재전송인데 에러로 보임 | 3-4의 `Idempotency-Key`로 같은 결과 응답 |
| 5 | 재고 부족 실패도 PENDING으로 복구 | PG 승인 후 재고 부족으로 보상 취소되면 주문이 PENDING으로 돌아가 재시도가 가능 | 재시도해도 같은 이유로 실패. 재시도 불가 사유를 구분하지 않음 | 실패 원인별로 CANCELED/FAILED 분리 (OrderStatus 확장 여부 결정 필요) |
