# 알려진 한계 (phase-03 진행 중 정리)

phase 파일에 작업으로 잡혀 있지 않지만, 대화에서 확인된 구멍을 기록해 둔다. 지금은 의도적으로 두고 넘어간다.
phase-03 마지막 질문("PG 승인은 성공했는데 서버가 죽으면?")의 재료이기도 하다.

| # | 한계 | 현재 동작 | 영향 | 풀려면 |
|---|---|---|---|---|
| 1 | 방치된 PENDING 주문이 정리되지 않음 | 주문하기를 누르고 결제 없이 나가면 PENDING 행이 계속 쌓임. 반복하면 주문번호가 다른 행이 N개 생김 | 재고는 승인 시 차감이라 영향 없음. 데이터 증가, 반복 호출에 무방비 | 만료 배치(일정 시간 지난 PENDING → CANCELED/EXPIRED), rate limit |
| 2 | PAYING에서 영구히 남을 수 있음 | PG 타임아웃, 서버 다운, 보상 취소 실패 시 PAYING 유지 | 돈은 나갔는데 주문이 PAID가 아닐 수 있음 | 오래된 PAYING을 PG에 조회해 완료 또는 복구하는 스케줄러(결제 상태 대사) |
| 3 | 결제 조회 API 없음 | `PaymentClient`에 승인(approve), 취소(cancel)뿐 | 2번을 풀 수단이 없음 | `PaymentClient`에 결제 조회 메서드 추가 |
| 4 | ~~선점에 실패한 요청이 예외를 그대로 받음~~ **(3-4에서 해결)** | 같은 `Idempotency-Key`의 재요청은 첫 결과를 돌려주거나 `409 PAYMENT_IN_PROGRESS`를 받음. 키가 다른 새 시도는 여전히 주문 상태 충돌(`STATE_CONFLICT`)을 받음 | - | - |
| 5 | 재고 부족 실패도 PENDING으로 복구 | PG 승인 후 재고 부족으로 보상 취소되면 주문이 PENDING으로 돌아가 재시도가 가능 | 재시도해도 같은 이유로 실패. 재시도 불가 사유를 구분하지 않음 | 실패 원인별로 CANCELED/FAILED 분리 (OrderStatus 확장 여부 결정 필요) |
| 6 | **주문서가 주문 시점 상품 정보를 보존하지 않음 (설계 결함)** | `orders`에 `product_id`, `quantity`, `total_price`만 저장. 상품명과 단가는 저장하지 않음 | `Product.update()`로 이름이나 가격이 바뀌면 주문 이력 조회 시 바뀐 정보가 보임. 영수증과 CS에서 주문 내용이 달라질 수 있음. 결제 금액 검증은 `total_price`가 있어 안전 | Flyway로 `orders`에 `product_name`, `unit_price` 스냅샷 컬럼 추가, `Order.create`에서 복사, `OrderResponse`에 노출. `@ManyToOne`으로 바꿔도 해결되지 않음(현재 상품을 가리키므로) |

| 7 | 멱등키가 IN_PROGRESS로 영구히 남을 수 있음 | PG 타임아웃, 보상 취소 실패, 서버 다운, 키 성공 기록 실패 시 키가 `IN_PROGRESS`로 남아 같은 키의 재요청이 계속 `409 처리 중`을 받음 | 2번(PAYING 고착)과 같은 원인. 클라이언트가 재시도 한도까지 "처리 중"만 받게 됨 | 결제 조회/대사로 PAYING을 확정할 때 멱등키 상태도 함께 확정 |
| 8 | 멱등키 만료·정리가 없음 | `idempotency_key` 행이 계속 쌓임 | 데이터 증가. 재사용 위험은 없음(UNIQUE) | 일정 기간 지난 확정 키를 지우는 배치 |
| 9 | 새 시도(다른 키)가 PAYING 주문에 오면 거절됨 | 결제창을 다시 열어 새 키로 요청해도 주문이 PAYING/PAID면 `STATE_CONFLICT`. 이 거절도 새 키에 FAILED로 기록됨 | 돈은 안전. 다만 PAYING이 고착되면(2번) 사용자가 재결제할 방법이 없음 | 2번과 함께 해결 |
| 10 | 클라이언트 재시도는 만들지 않음 | 서버는 `PAYMENT_IN_PROGRESS`를 구분되는 코드로 내려주기만 함 | 클라이언트가 같은 키로 재시도해야 하고, 한도 후에는 "실패"가 아니라 "확인 중"으로 안내해야 함(이중 결제 방지) | 클라이언트 구현 범위 |

> 6번은 프로젝트 목표(동시성 제어 학습)의 대상이 아니라서 의도적으로 고치지 않고 기록만 한다. 실제 서비스라면 가장 먼저 고칠 항목이다.
