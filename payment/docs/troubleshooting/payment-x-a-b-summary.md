## 1. 출발점: X의 문제

### 정합성

| 문제 | 무슨 일이 있었나 | 근거 |
|---|---|---|

| 에러가 나면 결제가 됐는지 모른다 | PG 타임아웃이면 주문 `PAYING`, 멱등키 `IN_PROGRESS`만 남고 `Payment`가 없었다. 대사할 때 어떤 `paymentKey`로 무엇을 조회해야 하는지 기록이 없었다 | 같음 |

## 2. A: 재고 차감을 PG 앞으로

- `startPaying`에서 주문 선점과 재고 차감을 한 트랜잭션으로 묶었다. 재고가 없으면 PG를 부르지 않는다.
- 해결: 경합 때 PG 낭비(200/199 → 1/0), 진 요청 지연(655~792ms → 18~230ms), 인기 상품 몰림(701 → 588ms).
- 남은 것: 정합성 문제는 그대로였다. 트랜잭션도 여전히 4번이었다.
- 상세: `payment-stock-before-pg-result.md`, `payment-stock-deduction-timing.md`

## 3. B: 결제 모델 재설계 (phase-04 4-2+)

- `Payment`를 PG 호출 **전에** `REQUESTED`로 만든다. (멱등키, `paymentKey`, 금액 저장)
- 멱등키를 `payment.idempotency_key` 컬럼으로 옮기고, `idempotency_key` 테이블은 V9에서 삭제했다.
- `PAYING`(진행 중)과 `PAYMENT_UNKNOWN`(결과 모름)을 나눴다. 타임아웃이면 `PAYMENT_UNKNOWN`으로 가서 대사로 확정한다.
- 확정 실패는 주문 `FAILED`로 끝낸다. 되돌아가는 간선이 없고, 재시도는 새 주문으로 한다.
- 재고 부족과 요청 금액 불일치도 PG 호출 전 거절로 기록한다. (주문 `FAILED`, `Payment FAILED` + `failure_code`)
- 트랜잭션: 이긴 요청 4 → 2번, 진 요청 3 → 1번.
- 해결: 1절의 정합성 문제 4개 모두. 재현 테스트 8개 통과.

## 5. 알게 된 것

### 5-1. B의 효과를 가르는 건 "상품 행 하나에 몰리느냐"다

| A → B 커넥션 대기 (ms) | 재고 경합 없음 | 재고 경합 있음 |
|---|---|---|
| 상품 행에 몰리지 않음 | H200-분산: 155 → 76 (절반) | C200-분산: 111 → 53 (절반) |
| 상품 행 하나에 몰림 | H200-공유: 252 → 255 (같음) | C200-집중: 0 → 140 (나빠짐) |

- 몰리지 않으면 커넥션 대기는 트랜잭션 수에 비례한다. 4번 → 2번이 그대로 절반으로 나타났다.
- 몰리면 상품 행 락 앞의 한 줄이 전체 시간을 정한다. H200-공유에서 B의 `startPaying` 최대값 479ms ≈ 200건 × 행을 쥐는 시간 약 2.4ms.

### 5-2. C200-집중에서 B가 느린 건 "실패를 기록하는 기능"의 비용이다

- B의 진 요청만 199건이 약 2ms 간격으로 한 건씩 끝났다. 같은 ms에 둘이 끝난 적이 없다. A·X는 43~54%가 같은 ms에 몰려 끝났다. (로그 타임스탬프)
- T1에서 B의 진 요청은 상품 행을 잠근 채 `Payment FAILED` INSERT, 주문 `FAILED` UPDATE, COMMIT을 한다. A·X는 바로 롤백한다.
- 그 줄이 커넥션 10개를 쥐고 있어서, PG에서 320ms에 돌아온 이긴 요청이 140ms를 기다렸다. A·X에서는 이긴 요청이 돌아왔을 때 진 요청이 이미 다 끝나 있었다. (A 마지막 진 요청 265~285ms, B 440~511ms)
- X·A는 재고 부족을 실패로 기록하지 않았다. 같은 기능을 같은 방식(락 안에서 기록 후 커밋)으로 넣었다면 X·A도 같은 줄이 생겼을 것이다. (측정 안 함) 그래서 이 차이는 "B가 느려졌다"보다 "원자적으로 실패를 기록하는 기능의 비용"이다.

| 이전 해석 | 고친 해석 | 근거 |
|---|---|---|
| 상품 행 락 대기는 거의 없다 (granularity 2-7) | 있다. 상품 하나에 몰리면 커넥션 대기 속에 섞여 보이지 않았을 뿐이다 | H200-분산 / 공유 비교 |

## 7. 결론 (사용자 작성)

### X → A → B 개선은 맞는 방향이었나?

맞는 방향이었다고 본다. (2026-11-24)
- 주문 하나에 결제 하나로 깔끔하게 매핑된다. 일정 시간 안에 결제가 매핑되지 않은 주문은 나중에 스케줄링으로 치우면 된다. (`PENDING → EXPIRED`, phase-04 4-4)
- 행 관리 측면에서 좋다. 시도마다 기록이 남아 추적 로그로 보기에도 좋다.
- 우리 쪽의 장애나 이슈를 외부사(PG)까지 전파하지 않는다. 재고가 없으면 PG를 부르지 않고, 확정 실패한 주문을 같은 주문번호로 다시 보내지 않는다.

### C200-집중의 손해를 어떻게 볼 것인가?

정합성 측면에서는 충분히 좋은 쪽이라고 본다. 다만 품절 폭주 때 진 요청이 상품 행 락을 쥔 채 커넥션을 붙잡는 구조라, 이것 때문에 추가 장애가 생길 것이 우려된다. 락 전 재고 조회로 풀어 봐야 한다. (2026-11-24)

### 측정의 한계

- 노트북 한 대, 가짜 PG 300ms, 커넥션 풀 10개, 시나리오마다 3회. 운영 환경의 절대 수치가 아니라 버전 간 비교와 병목 위치를 찾는 데 쓴 값이다.
- C200-집중의 이긴 요청은 실행당 1건씩 3건뿐이다. B에서는 같은 시나리오인데 실행마다 428~498ms로 흔들렸다.
- "rest"(SQL 실행 + 행 락 대기 + 코드)는 락 대기와 SQL 실행을 나눠 재지 않았다. 상품 행 락 대기는 로그 타임스탬프와 SQL 목록으로 추정했다.
