# 결제 승인: 요청 1건이 트랜잭션을 너무 잘게 나눠 여는 문제

> 상태: **개선 B 측정 완료 — 부하 중 개선 없음** (2-9). 트랜잭션 수가 아니라 요청당 DB 작업 시간이 병목으로 보인다. (phase-04 진행 중, `payment-stock-deduction-timing.md` k6 측정 중에 발견한 별도 문제)
> 2-1, 2-2는 단건 실행의 SQL 로그·트랜잭션 로그·Hibernate 세션 통계로 확인했다. 2-3의 커넥션 풀 경합 가설은 2-7에서 실측으로 확인했다. (2026-11-19) 개선은 아직 적용하지 않았다.

---

## 1. 배경

결제 승인은 아래 순서로 호출된다. 각 Service 메서드가 `@Transactional`이라 호출마다 커넥션을 빌리고 BEGIN/COMMIT을 한다.

```
PaymentApprovalFacade.approve()        (트랜잭션 없음)
 ├ IdempotencyService.begin()          트랜잭션
 ├ PaymentFacade.approve()             (트랜잭션 없음)
 │  ├ PaymentStateService.startPaying()   트랜잭션
 │  ├ PG 승인 호출                         (트랜잭션 밖)
 │  ├ PaymentStateService.complete()      트랜잭션
 │  └ (실패 시) PG 취소 → revertToPending()  트랜잭션
 └ IdempotencyService.succeed() / fail()  트랜잭션
```

PG 호출을 트랜잭션 밖으로 빼는 것(ARCHITECTURE 4, 5-2)은 의도한 설계다.
문제는 **PG 호출과 상관없는 구간까지** 트랜잭션이 나뉘어 있다는 점이다.

## 2. 문제 (가설)

### 2-1. 요청 1건당 트랜잭션 4~5번 (비관적 락 구현 기준, 실측)

**측정 방법:** 재고 1인 상품에 주문 A, B를 만들고 A → B 순서로 하나씩 승인했다. B는 PG 승인까지 간 뒤 `complete`에서 재고 부족으로 롤백되므로, 동시 실행 없이도 "경합에서 진 요청"과 같은 경로를 탄다.
- 서버: local 프로필, 가짜 PG 지연 0, SQL 로그 켬
- 추가 옵션: `--spring.jpa.properties.hibernate.generate_statistics=true --logging.level.org.hibernate.session.metrics=debug --logging.level.org.springframework.orm.jpa.JpaTransactionManager=debug`
- Hibernate 7은 세션 통계를 `org.hibernate.session.metrics` 카테고리에 **DEBUG**로 남긴다. `generate_statistics`만 켜면 아무것도 찍히지 않는다.
- 결과: PG 승인 2회, 취소 1회, 최종 재고 0. A 200(70ms), B 409(62ms)

| # | 트랜잭션 | 실행된 SQL (실행 순서) | 이긴 요청 | 진 요청 |
|---|---|---|---|---|
| 1 | `IdempotencyService.begin` | 주문 `FOR UPDATE` → 키 SELECT → 키 INSERT | 커밋, SQL 3 | 커밋, SQL 3 |
| 2 | `startPaying` | 주문 `FOR UPDATE` → (커밋 시 flush) 주문 UPDATE | 커밋, SQL 2 | 커밋, SQL 2 |
| | PG 승인 | | | |
| 3 | `complete` | 주문 `FOR UPDATE` → **Payment INSERT** → 상품 `FOR UPDATE` → (커밋 시 flush) 주문 UPDATE, 상품 UPDATE | 커밋, SQL 5 | **롤백**, SQL 3 |
| | PG 취소 | | | 진 요청만 |
| 4 | `revertToPending` | 주문 `FOR UPDATE` → (커밋 시 flush) 주문 UPDATE | | 커밋, SQL 2 |
| 5 | `succeed` / `fail` | 키 SELECT → (커밋 시 flush) 키 UPDATE | 커밋, SQL 2 | 커밋, SQL 2 |
| | **합계** | | **트랜잭션 4, 커넥션 4, SQL 12** | **트랜잭션 5, 커넥션 5, SQL 12** |

- 트랜잭션 수와 순서는 코드로 셌던 값과 같다. 트랜잭션마다 Hibernate 세션 1개, 커넥션 획득 1회였다.
- 단건이라 커넥션 획득 시간은 0.01ms 수준이다. 대기 시간은 부하를 걸어야 보인다. (6번 체크리스트의 다음 항목)

**코드만 읽었을 때 안 보였던 것**
- **진 요청도 Payment를 실제로 INSERT한 뒤 롤백한다.** `Payment`의 ID가 IDENTITY 방식이라 `save()` 시점에 바로 INSERT가 나간다. 재고 판정(상품 `FOR UPDATE`)보다 앞이다. DB에서 결제 ID 2715, 2717이 비어 있는 것으로 확인했다. (각각 진 요청 B가 쓰고 롤백한 번호)
- **UPDATE는 메서드 안이 아니라 커밋 직전 flush에서 나간다.** `complete`에서는 상품 `FOR UPDATE` → 재고 판정 → 커밋 직전에 주문·상품 UPDATE 순서다. 주문 행 락은 트랜잭션 첫 SQL부터 커밋까지 쥔다.
- UPDATE가 바뀐 컬럼만이 아니라 모든 컬럼을 쓴다. (`@DynamicUpdate` 없음) 상품 UPDATE에는 `version` 조건도 붙는다. (phase-02 낙관적 락의 `@Version`) 비관적 락 경로에서도 버전 검사가 같이 일어난다.

- 원자적 쿼리 구현(`AtomicUpdatePaymentStateService`)은 `FOR UPDATE` 대신 조건부 UPDATE를 쓰지만 트랜잭션 수는 같다.
- 3번 롤백과 4번은 재고 판정 시점 문제(`payment-stock-deduction-timing.md`)에서 오는 낭비라 이 문서에서는 따로 다루지 않는다.

### 2-1-1. 단건 구간별 소요 시간 (부하 측정의 기준값, 실측)

**측정 방법:** `PaymentSegmentTimer`(측정 전용 계측)가 요청 1건을 구간별로 재 `payment.timing` 로거에 한 줄로 남긴다.
- 서버: local, SQL 로그 끔, 가짜 PG 지연 300ms, `--logging.level.payment.timing=debug`
- 2-1과 같은 방식(재고 1, A → B 순서)을 워밍업 1회 + 3회 반복했다. 아래는 워밍업을 뺀 3회 평균이다. (2026-11-19)
- 워밍업 첫 요청의 `begin`은 40.9ms로, 이후(6~8ms)보다 컸다. 첫 호출 비용으로 보고 제외했다.

| 구간 | 종류 | 이긴 요청 | 진 요청 |
|---|---|---|---|
| `begin` | DB | 6.9ms | 11.0ms |
| `startPaying` | DB | 4.0ms | 6.6ms |
| `pgApprove` | PG | 303.6ms | 305.3ms |
| `complete` | DB | 24.9ms (커밋) | 25.9ms (롤백) |
| `pgCancel` | PG | | 303.2ms |
| `revertToPending` | DB | | 13.3ms |
| `succeed` / `fail` | DB | 8.9ms | 8.6ms |
| 기타 (Facade 자체, 예외 처리) | | 0.3ms | 2.2ms |
| **서버 안 합계** | | **348.6ms** | **676.2ms** |
| └ DB 구간 합계 | | 44.7ms (트랜잭션 4개) | 65.4ms (트랜잭션 5개) |
| └ PG 구간 합계 | | 303.6ms | 608.5ms |
| curl 전체 응답 시간 | | 351ms | 680ms |

- 단건에서도 응답 시간은 PG가 대부분(87~90%)을 차지한다. DB 구간은 이긴 요청 약 45ms, 진 요청 약 65ms다.
- **부하 측정의 기준값:** 부하에서 DB 구간 합계가 이 값보다 크게 늘면 커넥션 대기나 락 대기가 생긴 것이고, PG 구간이 늘면 PG(또는 스레드) 쪽 문제다.
- 2-3의 "실패 응답이 PG 왕복보다 130~230ms 더 걸렸다"와 비교하면, 단건에서도 이미 약 65ms(DB 구간)가 붙는다. 부하 때문에 늘어난 몫은 그 차이인 **약 65~165ms**다. (서로 다른 측정을 비교한 것이라 대략적인 값이다)
- **이 기준값으로 해피 케이스(1000건, 스레드 200)의 기대 시간을 계산할 수는 없다.**
  - 스레드만 보면 1000 ÷ 200 × 350ms ≈ 1.75초다. 하지만 DB 구간은 커넥션 10개로만 진행되는데 이 식은 그걸 무시한다.
  - 커넥션만 보면 1000건 × 45ms ÷ 10 ≈ 4.5초가 하한이다. 그런데 실측(3.5초)이 이 하한보다 빠르다.
  - 따라서 단건 DB 구간(45ms)은 부하 상황의 트랜잭션 시간을 대표하지 못한다. 워밍업이 부족해 콜드 비용이 섞였을 가능성이 있다. (추정)
  - 이 값은 기대 시간 계산이 아니라, 부하에서 어느 구간이 늘었는지 비교하는 출발점으로만 쓴다. 부하 중 트랜잭션 시간은 직접 잰다.
- **설명하지 못한 것:** `complete`가 단건인데도 21~29ms로 다른 트랜잭션(4~10ms)보다 길다. SQL이 5개로 가장 많긴 하지만, SQL 로그를 켜고 PG 지연을 0으로 둔 2-1 측정에서는 12ms였다. 원인은 확인하지 않았다.

### 2-2. 같은 주문 행을 여러 번 잠근다
- 주문 행 `FOR UPDATE`가 요청 1건에 3~4번 일어난다. (실측: 이긴 요청 3번, 진 요청 4번)
- 1번(`begin`)과 2번(`startPaying`)은 PG 호출 전에 연달아 일어나는데도 트랜잭션이 나뉘어 있다. 둘 다 "이 주문을 내가 처리한다"를 확인하는 관문이다.
- 두 관문 사이에 틈이 있어, 1번 커밋 후 2번 전에 실패하면 멱등키만 `IN_PROGRESS`로 남는다. (락 타임아웃 등. PG는 호출되지 않았는데 재요청이 계속 "처리 중"을 받는다)

### 2-3. 커넥션 풀 경합
- Hikari 기본 풀 크기는 10이다. (설정 파일에 별도 지정 없음)
- 100건이 동시에 들어오면 커넥션 10개를 놓고 400~500번 빌리기 경쟁을 한다.
- `payment-stock-deduction-timing.md` k6 측정(100건, PG 지연 300ms)에서 실패 응답이 PG 왕복(600ms)보다 약 130~230ms 더 걸렸다. 이 차이의 유력한 후보가 커넥션 대기와 주문 행 락 대기다. **확인하지 않은 추정이다.**
- 같은 문서의 해피 케이스 기준선(재고 1000, 주문 1000, 스레드 200, PG 지연 300ms)이 이 가설의 추가 정황이다.
  - PG 대기만 보면 1000건 ÷ 스레드 200 × 300ms ≈ 1.5초면 끝나야 하는데 결제 구간이 3.5초였다.
  - 그동안 상품 조회가 평균 1.4초로 느려졌고, 경합(재고 1) 때와 거의 같았다. → PG 대기보다 DB 쪽 직렬화가 시간을 지배하는 것으로 의심된다. (측정 환경의 CPU 경합 가능성도 있음)

### 2-4. 200건 동시 해피 케이스 (실측, 2026-11-19)

**왜 200건인가:** 요청 수를 Tomcat 스레드 수(200)와 같게 맞추면 스레드 줄서기가 없어진다. 그러면 늘어난 시간은 좁은 길(커넥션 10개, 행 락) 때문이라고 볼 수 있다. 1000건 해피 케이스는 두 가지가 섞여 있었다.

- 조건: 재고 200, 주문 200건 동시 승인 (전부 성공), PG 지연 300ms, 스레드 200, SQL 로그 끔, `payment.timing` 켬
- 실행: `k6 run -e ORDERS=200 -e STOCK=200 k6/stock-contention.js`
- 결과: 200건 모두 성공, PG 승인 200 / 취소 0, 최종 재고 0, 락 타임아웃·Hikari 타임아웃·ERROR 로그 0건

| 구간 | 단건 (2-1-1) | 200건 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|---|
| `begin` | 6.9ms | 73.9ms | 68.2 | 158.0 | 195.8 |
| `startPaying` | 4.0ms | 50.4ms | 59.8 | 97.9 | 160.1 |
| `pgApprove` | 303.6ms | 301.3ms | 300.7 | 305.0 | 307.7 |
| `complete` | 24.9ms | 110.5ms | 100.0 | 227.5 | 294.5 |
| `succeed` | 8.9ms | 108.9ms | 104.8 | 219.4 | 274.3 |
| **DB 구간 합계** | **44.7ms** | **343.7ms** | 441.6 | 483.9 | 495.3 |
| 서버 total | 348.6ms | 645.0ms | 743.3 | 784.7 | 795.7 |
| **k6 응답 시간 (고객 체감)** | 351ms | **657.4ms** | 752.5 | 799.9 | 807.4 |

**확인한 것**
- 고객 체감 응답 시간이 단건 351ms에서 평균 657ms로 약 1.9배, 중앙값 기준으로 2.1배가 됐다.
- **늘어난 시간은 거의 전부 DB 구간이다.** DB 구간 45ms → 344ms (약 +300ms). PG 구간은 300ms 그대로다.
- 스레드 대기(k6 응답 − 서버 total)는 평균 약 12ms로 거의 없다. 설계한 대로 스레드 줄서기는 제거됐다.
- **상품 행을 잠그는 `complete`만 늘어난 게 아니다.** 상품 행을 건드리지 않는 `succeed`(자기 멱등키 행만 UPDATE)도 `complete`와 거의 같이(약 109ms) 늘었다. `begin`, `startPaying`도 자기 주문 행만 잠그는데 10배 이상 늘었다.

**해석 (추정, 아직 확인하지 않음)**
- 서로 다른 행만 건드리는 트랜잭션까지 고르게 느려졌으므로, 이 규모에서는 **상품 행 락보다 커넥션 풀 대기가 주원인**일 가능성이 높다.
- 계산도 맞아떨어진다. 요청 200건 × DB 구간 45ms ÷ 커넥션 10개 ≈ 0.9초. 실제로 결제 처리가 이어진 구간은 약 0.8초였다. 커넥션 10개가 쉬지 않고 일한 시간과 비슷하다.
- 다만 지금 계측은 "커넥션을 기다린 시간"과 "SQL을 실행한 시간"을 나누지 못한다. MySQL 커밋 경합(redo log flush)도 모든 트랜잭션을 고르게 느리게 만들 수 있어서, 커넥션 대기라고 단정하려면 Hikari 대기 시간을 따로 재야 한다.

### 2-5. 1000건 동시 해피 케이스, 결제만 (실측, 2026-11-19)

2-4와 같은 조건에서 주문 수와 재고만 1000으로 바꿨다. (`k6 run -e ORDERS=1000 -e STOCK=1000 k6/stock-contention.js`)
`payment-stock-deduction-timing.md` 3단계의 1000건 해피 케이스는 상품 조회 트래픽이 섞인 혼합 부하였다. 이번에는 결제만 보냈다.
- 결과: 1000건 모두 성공, PG 승인 1000 / 취소 0, 최종 재고 0, 락 타임아웃·커넥션 타임아웃·ERROR 로그 0건, 결제 처리 구간 약 3.15초

|---|---|---|---|---|
| `begin` | 6.9ms | 73.9ms | 94.9ms | 202.7 |
| `startPaying` | 4.0ms | 50.4ms | 53.9ms | 173.0 |
| `pgApprove` | 303.6ms | 301.3ms | 301.0ms | 303.7 |
| `complete` | 24.9ms | 110.5ms | 109.8ms | 231.8 |
| `succeed` | 8.9ms | 108.9ms | 103.0ms | 238.7 |

**확인한 것**
- 고객 체감 응답 시간은 평균 2.0초다. 혼합 부하 때(1.94초)와 거의 같아서, 그때 섞여 있던 상품 조회 트래픽은 결제 응답 시간에 큰 영향이 없었다.
- **서버 안 처리 시간은 200건 때와 거의 같다.** (645ms → 663ms, DB 구간 344ms → 362ms) 요청이 5배가 돼도 DB 구간은 늘지 않았다.
- **늘어난 1.34초는 계측(Facade) 바깥에서 생겼다.** 200건 때는 이 차이가 12ms였다.

**해석**
- DB에 동시에 들어갈 수 있는 요청은 Tomcat 스레드 수(200)로 이미 제한된다. 그래서 1000건이 와도 DB가 받는 압력은 200건 때와 같고, 나머지 800건은 스레드를 기다린다.
- k6 − 서버 total(1.34초)은 대부분 스레드 대기로 본다. 200건 때 이 값이 12ms였으므로 필터·JSON 변환·네트워크 몫은 작다. (스레드 대기를 직접 잰 것은 아니다)
- 계산으로도 맞는다. 스레드 하나가 요청 하나를 약 0.66초 쥔다. 200개 스레드로 1000건을 처리하면 5묶음이고, 각 묶음의 응답은 0.66 / 1.33 / 1.99 / 2.65 / 3.31초다. 평균은 약 **1.99초**, 마지막은 약 3.3초다. 실측(평균 2.0초, 최대 3.48초, 처리 구간 3.15초)과 맞는다.
- **따라서 1000건의 2초는 "스레드 1개가 요청 1건을 쥐는 시간(0.66초) × 줄 선 묶음 수"다.** 그 0.66초 중 DB 구간이 단건 45ms에서 360ms로 늘어난 것이 커넥션 10개 경합(2-4의 추정)이다. 이 경합이 스레드를 쥐는 시간을 약 2배로 늘렸고, 그만큼 줄 선 요청의 대기도 2배가 됐다.
- 스레드를 쥐는 시간이 단건 수준(0.35초)이었다면 같은 계산으로 평균은 약 1.05초다. **DB 경합이 고객 체감 시간의 약 절반(약 0.95초)을 만든 셈이다.** (추정, 계산값)

### 2-6. 지금까지의 정리 (2-1 ~ 2-5 종합, 2026-11-19)

**1. 커넥션 10개가 꽉 찬 상태에서 요청 1건은 약 0.66초 걸린다.**
- 정확히는 "스레드 200개가 커넥션 10개에 동시에 몰린 상태"의 값이다. 동시 요청이 적으면 더 짧다. (1건이면 0.35초. 그 사이 값은 측정하지 않았다)
- 처리량으로 바꾸면 **초당 약 300건**이 현재 구조의 한계다. 스레드 200 ÷ 0.66초 ≈ 300건/초. 실측도 1000건을 약 3.15초에 처리했다. (약 317건/초)

**2. 동시 요청이 스레드 수(200)를 넘으면, 넘은 요청은 스레드 앞에서 줄을 선다.**
- 200건을 넘는 요청은 DB를 더 느리게 만들지 않는다. 200건과 1000건의 DB 구간이 344ms와 362ms로 거의 같았다.
- 늘어나는 것은 스레드를 기다리는 시간이다. (1000건에서 약 1.34초)

**3. 한 번에 들어오는 요청이 늘면 응답 시간은 거의 직선으로 늘어난다.**
계산식: `평균 ≈ 0.66초 × (N/200 + 1) / 2`, 가장 늦은 요청 ≈ `0.66초 × N/200`

| 동시 요청 | 평균 응답 | 가장 늦은 요청 | 비고 |
|---|---|---|---|
| 1000 | 약 2.0초 | 약 3.3초 | 실측 평균 2.0초, 최대 3.48초 |
| 2000 | 약 3.6초 | 약 6.6초 | 계산값 |
| 5000 | 약 8.6초 | 약 16.5초 | 계산값 |

- 계산값은 실제로는 다른 한계에 먼저 걸릴 수 있다. 클라이언트 타임아웃이 대표적이다. 고객 쪽이 포기해도 서버는 결제를 계속 처리하므로, 결제에서는 "고객은 실패로 봤는데 돈은 나간" 상황이 생길 수 있다. Tomcat 연결 수 같은 서버 설정 한계도 있다.

**4. 실제 서비스에서 볼 숫자는 "한 번에 몇 건"보다 "초당 몇 건"이다.**
- 지금 테스트는 1000건을 한순간에 보내서, 줄이 한 번 생겼다가 약 3초 만에 사라졌다.
- 실제 트래픽은 계속 들어온다. 초당 요청이 처리량(약 300건/초)보다 **적으면** 줄이 쌓이지 않고 응답은 0.35~0.66초 근처에 머문다. **많으면** 줄이 계속 길어지고 응답 시간이 끝없이 늘어난다.
- 그래서 현재 구조의 핵심 숫자는 "한 건 0.66초"보다 **"초당 약 300건 한계"**다.

**5. 문제는 두 겹이다.**
- 커넥션 10개 경합이 요청 1건이 스레드를 쥐는 시간을 0.35초에서 0.66초로 늘린다. (DB 구간 45ms → 약 360ms)
- 그 결과 처리량이 줄고, 넘친 요청의 스레드 줄서기가 길어진다. 1000건 기준 고객 체감 2초 중 약 0.95초가 이 경합 때문이다. (계산값)
- ~~아직 확인하지 않은 것: DB 구간 증가가 정말 커넥션 대기인지.~~ → 2-7에서 확인했다. 증가분 거의 전부가 커넥션 대기다.

### 2-7. DB 구간 쪼개기: 커넥션 대기 / COMMIT / 나머지 (실측, 2026-11-19)

**질문:** 200건에서 DB 구간이 45ms → 약 360ms로 늘어난 것이 정말 커넥션 풀 대기인가? (2-4, 2-6의 추정)

**측정 방법:** 측정 전용으로 DataSource를 감쌌다. (`JdbcTimingDataSource`, `JdbcTiming`, `JdbcTimingConfig`)
- `getConnection()` 시간 = 커넥션 풀 대기. Spring + JPA는 트랜잭션 시작 시 커넥션을 빌리므로 트랜잭션별 대기 시간이다.
- `Connection.commit()` 시간 = COMMIT. (롤백은 재지 않는다)
- 나머지 = DB 구간 − 커넥션 대기 − COMMIT. SQL 실행, 행 락 대기, 애플리케이션 코드가 여기 들어간다.
- `payment.timing`이 DEBUG일 때만 감싼다. 로그 형식: `complete=103.3ms(conn=85.6ms,commit=1.2ms)`
- 조건: 2-4와 같다. (PG 지연 300ms, SQL 로그 끔, 결제만) 단건은 워밍업 1회를 빼고 이긴 요청 3건 평균, 200건은 `k6 run -e ORDERS=200 -e STOCK=200 k6/stock-contention.js`

| 구간 | 단건: 전체 / 커넥션 대기 / COMMIT / 나머지 | 200건: 전체 / **커넥션 대기** / COMMIT / 나머지 |
|---|---|---|
| `begin` | 8.1 / 0.0 / 2.3 / 5.7 | 95.9 / **88.8** / 2.5 / 4.6 |
| `startPaying` | 5.4 / 0.0 / 1.9 / 3.6 | 70.3 / **65.4** / 2.3 / 2.6 |
| `complete` | 21.7 / 0.0 / 3.2 / 18.4 | 103.3 / **85.6** / 1.2 / 16.5 |
| `succeed` | 9.3 / 0.0 / 2.2 / 7.1 | 106.2 / **102.1** / 1.9 / 2.1 |
| **DB 구간 합계** | **44.4 / 0.0 / 9.6 / 34.8** | **375.7 / 342.0 / 7.9 / 25.8** |

(단위 ms. 200건 결과: 전부 성공, 최종 재고 0, 고객 체감 평균 690ms, 락·커넥션 타임아웃과 ERROR 로그 0건)

**확인한 것**
- **DB 구간 증가의 거의 전부가 커넥션 풀 대기다.** 늘어난 약 331ms 중 342ms가 커넥션 대기다. (나머지가 오히려 약 9ms 줄었다)
- **COMMIT은 늘지 않았다.** (9.6 → 7.9ms) MySQL 커밋 경합 가설은 틀렸다.
- **상품 행 락 대기도 거의 없다.** 200건이 같은 상품 행을 `FOR UPDATE`하는 `complete`의 나머지가 18.4 → 16.5ms로 그대로다. 커넥션 풀이 DB에 동시에 들어가는 요청을 10개로 줄이기 때문에, 상품 행 앞의 줄이 길어지지 않는 것으로 본다. (해석)
- 요청 1건이 커넥션을 4번 빌리고, 매번 평균 약 85ms를 기다린다. **트랜잭션 수(빌리는 횟수)만큼 대기가 곱해진다.**

**결론: 2-3의 가설("커넥션 풀 경합")이 실측으로 확인됐다.** 현재 구조에서 동시 요청이 몰릴 때의 병목은 커넥션 풀이고, 그 비용은 "요청당 커넥션을 빌리는 횟수(트랜잭션 수)"에 비례한다.

**개선 해석에 주는 의미 (적용 전 메모)**
- 트랜잭션 수를 줄이는 개선(5번 표)은 커넥션 대기 횟수를 직접 줄이므로 효과가 있을 것으로 예상한다. 
- 커넥션 풀 크기를 늘리면 대기는 줄겠지만, 지금은 커넥션 풀이 상품 행 락 앞의 줄을 막아 주고 있다. 풀을 키우면 병목이 상품 행 락으로 옮겨갈 수 있다. (5번 표의 "경합 지점만 옮겨간다"와 같은 이야기, 확인하지 않음)
- 재고 차감을 PG 호출 앞으로 옮기는 개선(`payment-stock-deduction-timing.md`)도 이 측정 방식으로 상품 행 락 대기가 "나머지"에 나타나는지 볼 수 있다.


### 2-8. 개선 A(재고 차감을 `startPaying`으로) 적용 후 같은 측정 (실측, 2026-11-19)

**질문:** A는 이긴 요청의 트랜잭션 수(4번)를 바꾸지 않는다. 그러면 해피 케이스는 그대로여야 하고, 상품 행 작업은 `complete`에서 `startPaying`으로 자리만 옮겨야 한다. 정말 그런가?

**조건:** 2-7과 같다. (PG 지연 300ms, SQL 로그 끔, 결제만, 서버 재기동 후 경합 100건 → 단건 → 200건 → 1000건 순서로 각 1회) 집계는 `k6/analyze_timing.py`.

| 구간 (200건) | 개선 전 (2-7): 전체 / 커넥션 대기 / COMMIT / 나머지 | 개선 후 |
|---|---|---|
| `begin` | 95.9 / 88.8 / 2.5 / 4.6 | 95.8 / 90.5 / 2.0 / 3.2 |
| `startPaying` | 70.3 / 65.4 / 2.3 / **2.6** | 166.9 / **148.9** / 1.3 / **16.7** |
| `complete` | 103.3 / 85.6 / 1.2 / **16.5** | 22.5 / **18.4** / 1.7 / **2.4** |
| `succeed` | 106.2 / 102.1 / 1.9 / 2.1 | 10.0 / 6.4 / 1.7 / 1.8 |
| **DB 구간 합계** | **375.7 / 342.0 / 7.9 / 25.8** | **295.2 / 264.2 / 6.8 / 24.1** |

| 고객 체감 (k6 `approve_latency_success` 평균) | 개선 전 | 개선 후 |
|---|---|---|
| 단건 | 0.35초 | 0.35초 (350ms, DB 43.5ms) |
| 200건 | 0.66~0.69초 | **0.60초** (p95 758ms) |
| 1000건 | 2.0초 | **1.85초** (p95 3.0초, 서버 안 `total` 평균 599ms) |

**확인한 것**
- **상품 행 작업의 "나머지"가 `complete` → `startPaying`으로 그대로 옮겨 갔다.** (200건: 16.5 → 2.4, 2.6 → 16.7) 크기는 변하지 않았으므로 PG 앞으로 옮겨도 상품 행 락 대기는 커지지 않았다. 1000건에서도 `startPaying` 나머지 평균 15.7ms, p95 23.1ms.
- **예상과 다른 점: 해피 케이스가 "그대로"가 아니라 조금 빨라졌다.** 200건 커넥션 대기 합이 342 → 264ms, 고객 체감 0.69 → 0.60초. 1000건도 2.0 → 1.85초.
- **커넥션 대기가 몰리는 위치가 바뀌었다.** 개선 전에는 네 트랜잭션에 고르게(65~102ms) 나뉘었는데, 개선 후에는 `begin`·`startPaying`(PG 앞)에 몰리고 `complete`·`succeed`(PG 뒤)는 거의 기다리지 않는다.

**해석 (확인하지 않음)**
- 상품 행 `FOR UPDATE`는 같은 상품 요청을 한 줄로 세운다. 줄을 서는 동안에도 커넥션을 쥐고 있으므로, 이 구간이 있는 트랜잭션이 풀을 오래 점유한다.
  - 개선 전: 이 구간이 PG **뒤**(`complete`)에 있어서, PG 300ms를 지나 다시 몰려온 요청들이 풀과 상품 행 앞에서 또 한 번 줄을 섰다.
  - 개선 후: 이 구간이 PG **앞**(`startPaying`)으로 옮겨 가 첫 줄서기와 합쳐졌다. 거기서 요청들이 한 줄로 정렬된 채 PG로 나가므로, PG 뒤 트랜잭션들은 도착 시점이 흩어져 거의 기다리지 않는다.
- 다만 **단발 측정이고**, 개선 전 200건도 실행마다 0.66~0.69초로 흔들렸다. 개선 폭(약 0.09초)은 그 흔들림보다 크지만, 여러 번 반복해 확인하지는 않았다.
- **A가 트랜잭션 수를 줄이지 않는다는 점은 그대로다.** 1000건의 1.85초는 여전히 대부분 스레드(200개) 앞 줄서기이고, 요청당 커넥션 대기 260ms대가 남아 있다. 병목 해소는 B의 몫이다.

### 2-9. 개선 B(트랜잭션 합치기, phase-04 4-2+) 적용 후 같은 측정 (실측, 2026-11-20)

- **진 요청도 같다.** 트랜잭션이 3번 → 1번이 됐는데 실패 응답은 216 → 214ms, 커넥션 대기는 173 → 169ms다.
- **대신 커넥션 한 번 빌리는 데 기다리는 시간이 늘었다.** 200건 기준 트랜잭션당 약 66ms(264 ÷ 4) → 약 139ms(278 ÷ 2). 빌리는 횟수가 줄어든 만큼 한 번의 대기가 길어져, 합이 그대로다.
- **부하가 없으면 줄었다.** 단건 DB 구간이 43.5 → 20.8ms. 커넥션 획득·BEGIN·COMMIT 왕복이 줄어든 몫으로 보인다. (COMMIT 합: 9.6ms(2-7 단건) → 약 4.3ms)
- **요청 1건이 DB에서 실제로 일하는 시간은 거의 그대로다.** 200건 기준 COMMIT + 나머지 = 30.9ms(2-8) → 30.2ms. 합친 것은 "빌리는 횟수"이지 "DB에서 하는 일"이 아니다.

**해석 (확인하지 않음)**
- 2-7의 결론 "대기는 트랜잭션 수만큼 곱해진다"는 **틀린 것으로 보인다.** 그때는 "트랜잭션당 약 85ms × 4번"으로 맞아떨어졌지만, 트랜잭션을 줄여도 합이 줄지 않았다.
- 대신 이렇게 설명된다: 200건이 한꺼번에 도착하면 커넥션 10개 앞에 줄을 선다. 줄이 빠지는 속도는 "요청 1건이 커넥션을 실제로 쥐고 일하는 시간(약 30ms)"으로 정해진다. 200건 × 30ms ÷ 10개 = 약 600ms 동안 줄이 빠지고, 평균 대기는 그 절반인 약 300ms다. 실측 278ms와 비슷하다.
  - 이 계산에는 트랜잭션 수가 들어가지 않는다. 쥐는 시간의 합이 같으면, 한 번에 쥐든 나눠 쥐든 줄의 길이는 같다.
  - 처리량 한계 "10개 ÷ 30ms ≈ 330건/초"도 2-6의 약 300건/초와 맞다.
- 그래서 부하 중 커넥션 대기를 줄이려면 **요청당 DB 작업 시간(나머지 약 27ms)을 줄이거나**, 동시 진입 수(풀 크기)를 바꿔야 한다. 트랜잭션 수는 부하가 없을 때의 지연(단건 -23ms)에만 효과가 있었다.
- 나머지 27ms가 무엇인지는 아직 모른다. (`startPaying` 24.5ms: 주문·상품 `FOR UPDATE`, 재고 UPDATE, Payment INSERT, 멱등키 조회. 단건에서는 7.6ms라 부하 중 늘어난 몫이 있다. 상품 행 락 대기일 가능성이 있지만 확인하지 않았다)

**설명하지 못한 것 (갱신)**
- 단건에서 `complete`의 나머지가 14.9ms로 여전히 길다. 상품 행 작업을 뺐는데도 그렇다. 그래서 "단건 `complete`의 약 18ms는 상품 행 처리 비용"이라는 추측은 **맞지 않는 것으로 보인다.** 그런데 200건에서는 `complete` 나머지가 2.4ms로 짧다. 단건은 1회 측정이라(개선 전은 3회 평균) 반복 측정이 필요하다. 남은 후보: `Payment` INSERT(IDENTITY), 이벤트 발행, 첫 요청 지연.


## 3. 원인 (추정)

- "PG 호출은 트랜잭션 밖"이라는 원칙을 지키려고 Facade에서 Service 메서드를 나눴는데, 나누는 기준이 **PG 호출 경계**가 아니라 **기능 단위(멱등키 / 주문 상태 / 결제 반영)**가 됐다.
- 멱등키가 별도 테이블·별도 Service라서, 주문 선점과 같은 트랜잭션에 넣기 어려운 구조다.

## 8. 학습 포인트

- 트랜잭션을 나누는 기준은 "외부 I/O 경계"다. 기능 단위로 나누면 PG 호출과 상관없는 구간까지 쪼개진다.
- 트랜잭션 하나하나는 짧아도, 횟수가 많으면 커넥션 빌리기·락 획득·커밋 왕복이 쌓인다.
- 같은 목적의 관문(멱등키 선점, 주문 선점)이 두 트랜잭션에 나뉘면 그 사이에 틈이 생긴다.
