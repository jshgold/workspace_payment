# 결제 승인: 락 전 재고 조회

> 작성: 2026-11-24. 출발점은 `payment-x-a-b-summary.md` 5-2, 6절 "품절 폭주". 상태: **방식 정리 완료, 구현·측정 전.**
> 결정 기록: `.harness/intent.md` 8절 "품절 폭주 대응"

## 1. 한 줄 요약

재고 0인 상품에 결제 요청이 오면 지금은 **상품 행 락 줄에 서서** 차례를 기다린 뒤 실패를 기록한다. 이것을 **줄에 서지 않고** 락 없이 재고를 읽어 바로 실패를 기록하도록 바꾼다.

## 2. 왜 하나

- B(4-2+)에서 재고 부족도 결제 시도로 기록하게 됐다. 진 요청은 상품 행 락을 쥔 채 `INSERT payment`, `UPDATE orders`, `COMMIT`을 한다. (`test-list.md` 1-8-T1)
- 그래서 C200-집중에서 진 요청 199건이 약 2ms 간격으로 한 건씩 지나갔고, 그 줄이 커넥션 10개를 붙잡았다. PG에서 돌아온 이긴 요청은 커넥션을 140ms 기다렸다. (summary 5-2)
- 이 손해는 결제 밖으로도 번진다. 경합 1000건에서 결제와 무관한 상품 조회가 A 591ms → B 1,021ms로 느려졌다. (`payment-stock-deduction-timing.md` "개선 B 후 같은 측정")
- 정합성(실패도 기록)은 유지하고, **실패를 기록하는 동안 상품 행 락을 쥐지 않게 하는 것**이 목표다.

## 3. 바뀌는 흐름 (`PessimisticLockPaymentStateService.startPaying`)

**지금**
```
멱등키 재전송 확인 → orders FOR UPDATE → 금액 검증
  → product FOR UPDATE → 재고 판정
      ├ 부족: Payment FAILED INSERT, orders FAILED, COMMIT   ← 상품 행 락을 쥔 채
      └ 충분: 재고 차감, orders PAYING, Payment REQUESTED INSERT, COMMIT
```

**바뀐 뒤**
```
멱등키 재전송 확인 → orders FOR UPDATE → 금액 검증
  → [락 없는 재고 조회]
      ├ 확실히 안 됨: Payment FAILED INSERT, orders FAILED, COMMIT   ← 상품 행 락 없이
      └ 될 수도 있음: product FOR UPDATE → 지금과 같은 판정·처리
```

- 락 없는 조회는 **"확실히 안 됨"을 걸러내는 데만** 쓴다. 통과한 요청은 락을 잡은 뒤 다시 판정하므로 초과 판매는 생기지 않는다.
- 같은 트랜잭션 안에서 하므로 커넥션을 더 빌리지 않는다. 트랜잭션 수(이긴 요청 2, 진 요청 1)는 그대로다.
- 잠그는 순서(orders → product)도 그대로다. 걸러진 요청은 product를 아예 잠그지 않는다.
- 응답, 상태 전이(`PENDING → FAILED`), 기록(`Payment FAILED` + `STOCK_NOT_AVAILABLE`)은 지금과 같다. 바뀌는 것은 상품 행 락을 잡느냐뿐이다.

## 4. 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 읽는 방법 | 엔티티가 아니라 **값만** 읽는다 (`stock`, `status`, `deletedAt`을 record로 프로젝션) | 아래 5-1 |
| 낡은 스냅샷 | **감수한다.** 실제로는 재고가 있는데 거절하는 "빡빡한 검증"이 드물게 생길 수 있다 | 아래 5-2 |
| 적용 범위 | **비관적 락 구현(`@Primary`)에만** 넣는다. 원자적 쿼리 구현에는 넣지 않는다 | 원자적 쿼리 방식이 성능에서 확실히 낫다고 보지 않아서, 비교 대상을 늘리지 않는다 (사용자 판단, 2026-11-24) |

## 5. 주의할 점

### 5-1. 엔티티로 먼저 읽으면 락 안의 판정이 낡은 값으로 이뤄진다

`findById`로 `Product` 엔티티를 먼저 읽으면, 뒤의 `findByIdForUpdate`는 DB에서 행을 잠그지만 **영속성 컨텍스트에 이미 있는 엔티티를 그대로 돌려준다.** 잠근 뒤의 최신 재고가 아니라 락 없이 읽은 예전 값으로 판정·차감하게 된다.
- 지금은 `@Version`이 UPDATE에서 이를 잡겠지만, `Product.version`은 제거 예정이라 기대면 안 된다.
- 그래서 엔티티를 만들지 않는 값 전용 조회를 쓴다. 영속성 컨텍스트에 아무것도 남지 않으므로 뒤의 `FOR UPDATE`는 지금처럼 최신 행을 읽는다.
- 판정 규칙(`삭제 안 됨 && 수량 > 0 && STOPPED 아님 && 재고 >= 수량`)은 `Product.canDecreaseStock`과 같은 것을 써야 한다. 규칙이 두 곳에 따로 쓰이지 않게 한 곳에 두고 양쪽에서 부른다. (구현 때 방법 확인)

### 5-2. 락 없는 조회는 트랜잭션 스냅샷을 본다

MySQL 기본 격리 수준(REPEATABLE READ)에서 락 없는 SELECT는 그 트랜잭션의 첫 일반 읽기(멱등키 재전송 확인) 시점의 스냅샷을 본다. 그사이 다른 결제가 실패해 재고가 복구됐다면 "재고 0"으로 보고 거절할 수 있다.

| 스냅샷과 실제가 다를 때 | 결과 | 위험 |
|---|---|---|
| 스냅샷엔 있음, 실제론 없음 | 락 줄로 간다 → 락 안에서 다시 판정해 거절 | 없음 (지금과 같음) |
| 스냅샷엔 없음, 실제론 있음 (복구 직후) | 락 없이 거절 | 판매 기회 하나를 놓침. 초과 판매는 아님 |

감수하는 이유 (2026-11-24 논의):
- 스냅샷과 실제의 차이는 보통 수 ms다. 그 사이에 "다른 결제가 실패해 재고 복구"가 끼어야 생기는 일이라, 일반 상품 판매에서 자주 있을 경우가 아니다.
- 이것까지 막으려면 격리 수준 조정 등 통제할 것이 늘어나는데, 얻는 것이 작다.
- 락 전 조회만의 문제가 아니다. 락 버전에서도 "복구 직전에 도착한 요청은 거절"되고, 재고를 주문 생성 시점에 잡는 구조로 바꿔도 같은 종류의 경합이 생긴다. 확인 시점과 복구 시점이 엇갈리는 것은 재고를 판정하는 모든 방식에 있다.

## 6. 설계 검토 (CLAUDE.md 3절)

| 항목 | 결과 |
|---|---|
| 외부 호출 전 시도 기록이 남는가 | 바뀌지 않는다. 걸러진 요청도 `Payment FAILED`로 남는다 |
| 결과 모름을 표현할 수 있는가 | 관계없다. PG를 부르지 않는 경로다 |
| 역행 간선이 생기는가 | 없다. 지금과 같은 `PENDING → FAILED`, 새 상태 없음 |
| 락·트랜잭션을 쥔 채 외부 호출하는가 | 없다. 오히려 쥐는 락이 줄어든다 |
| 같은 요청이 재전송되면 | 멱등키 확인이 먼저 돌아 같은 `STOCK_NOT_AVAILABLE`을 받는다. 지금과 같다 |

## 7. 예상과 측정 계획 (구현 후, 실행 전에 다시 설명한다)

**예상 (측정 안 함)**
- 상품 행 락 줄에는 승자가 커밋하기 전에 스냅샷을 잡은 요청만 선다. 커넥션 풀(10개)이 동시 진입을 제한하므로 약 10건 안팎으로 본다.
- 나머지는 커넥션 10개에서 동시에 실패를 기록한다. 같은 ms에 여러 건이 끝나는 모습(A·X처럼)이 다시 보일 것이다.
- 이긴 요청의 커넥션 대기(140ms)와 경합 중 상품 조회 지연이 A 수준에 가까워질 것이다.

| 측정 | 값 | 출처 |
|---|---|---|

**회귀 확인**
- `stockContentionApprovesOnlyWinner` (PG 승인 1 / 취소 0)
- 결제 패키지 테스트 전체
- 락 전 조회로 걸러진 요청이 상품 행을 잠그지 않았는지: SQL 로그에서 진 요청에 `product ... for update`가 없는지 확인
