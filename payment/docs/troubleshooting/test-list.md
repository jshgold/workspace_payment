# 결제 트러블슈팅 테스트 목록

1부는 X / A / B를 같은 조건으로 다시 잰 **재측정**이다. 2부는 조사하면서 그때그때 돌린 **이전 측정**으로, 개선 A·B를 결정한 근거다. 1부는 그 근거를 같은 조건으로 다시 확인하고, 일부 해석을 고쳤다.
이전 측정의 수치는 각 문서(조사 기록)에 그대로 두고 덮어쓰지 않는다. 재측정 결과는 이 문서 1부에만 채운다.

- **개선 X**: 재고를 PG 승인 뒤(`complete`)에서 차감, 멱등키는 별도 테이블
- **A**: 재고 차감을 PG 앞(`startPaying`)으로 (`7c545d4`, merge `5e7823f`)
- **B**: 멱등키를 `payment` 컬럼으로, 트랜잭션 합치기 (phase-04 4-2+, `ac773a8`)

문서 이름 줄임: stock-deduction-timing = `payment-stock-deduction-timing.md`, granularity = `payment-transaction-granularity.md`

# 1부. 재측정 시나리오 (X / A / B 같은 조건)

## 1-1. 왜 다시 재나

- 이전 측정은 질문이 생길 때마다 테스트를 만들어서, 버전마다 잰 시나리오·횟수·지표가 다르다. (예: A의 단건은 1회, 구간별 값 없음)
- 이전 해피 케이스는 모두 **상품 1개에 재고 N**이었다. 전부 성공해도 모든 요청이 같은 상품 행 `FOR UPDATE`에 줄을 서서, 커넥션 대기와 상품 행 락 대기가 섞여 있었다. (2-9의 정체 모를 "나머지 약 27ms")
- 그래서 **동시 요청 수**(커넥션 풀 효과)와 **상품 행 경합 정도**(행 락 효과)를 나눠서 잰다.

## 1-2. 측정 버전

| 버전 | 커밋 | 비고 |
|---|---|---|
| 개선 X | `2f25076` | X 구조이면서 계측(`PaymentSegmentTimer`, `JdbcTiming`)이 모두 있는 마지막 커밋. `73ce46c`·`4156c7b`는 계측이 없거나 일부만 있다 |
| A | `5e7823f` | A merge 커밋 |
| B | 현재 코드 (`ac773a8` + replay 금액 검사) | 금액 검사는 키가 이미 있을 때만 도는 비교라 측정에 영향 없음 |

- X·A는 V9 이전 스키마(`idempotency_key` 테이블)를 쓰므로, 지금 로컬 DB(V9 적용됨)로는 뜨지 않는다. 버전마다 git worktree + **빈 DB**를 만들어 각 버전의 Flyway로 처음부터 마이그레이션한다. 기존 `payment` DB는 건드리지 않는다.
- 세 버전 모두 빈 DB에서 시작하므로 데이터량도 같아진다.

| 락 구현 | 비관적 락 (`@Primary` 기본 구현) |

## 1-4. 남길 지표

| 지표 | 출처 |
|---|---|
| 고객 체감 응답 시간 (성공 / 실패 따로, 평균·p95) | k6 `approve_latency_success` / `approve_latency_failure` |
| 구간별 시간 | `payment.timing` 로그 → `k6/analyze_timing.py` |
| DB 구간 합 = 커넥션 대기 + COMMIT + 나머지 | 같음 |
| PG 승인 / 취소 횟수 | `GET /api/fake-pg/stats` |

| 트랜잭션 수·SQL 수 | T1에서만 (Hibernate 세션 통계) |

- 구간 이름이 버전마다 다르다. X·A: `begin`, `startPaying`, `pgApprove`, `complete`, `succeed`/`fail` (X의 진 요청은 `pgCancel`, `revertToPending`도) / B: `startPaying`, `pgApprove`, `complete`, `fail`
- 그래서 버전끼리 직접 비교하는 값은 **DB 구간 합, 커넥션 대기 합, COMMIT 합, 나머지 합, 고객 체감**이다. 구간별 값은 나란히 놓고 합쳐진 구간은 "합쳐짐"으로 표시한다.

## 1-5. 시나리오

공통: 상품 가격 10,000원, 주문 수량 1개. 주문 하나당 승인 요청 1번이고, 멱등키·`paymentKey`는 주문마다 다르다.
주문은 상품에 차례로 돌아가며 붙는다. (주문 i → 상품 i % 상품 수) "동시"는 모든 요청을 한꺼번에, "순차"는 앞 요청의 응답을 받은 뒤 다음 요청을 보낸다.

| 코드 | 시나리오 | 상품 수 | 상품당 재고 | 승인 요청 수 | 상품당 요청 | 실행 | 기대 결과 (성공 / 실패) | k6 옵션 |
|---|---|---|---|---|---|---|---|---|
| **H1** | 해피, 단건 | 1 | 1 | 1 | 1 | - | 1 / 0 | `-e ORDERS=1 -e STOCK=1` |
| **L1** | 경합, 진 요청 단건 | 1 | 1 | 2 | 2 | **순차** | 1 / 1 (두 번째가 실패) | `-e ORDERS=2 -e STOCK=1 -e SEQUENTIAL=true` |
| **C2** | 경합, 최소 | 1 | 1 | 2 | 2 | 동시 | 1 / 1 | `-e ORDERS=2 -e STOCK=1` |
| **H10-분산** | 해피, 상품 나눔 | 10 | 1 | 10 | 1 | 동시 | 10 / 0 | `-e ORDERS=10 -e STOCK=1 -e PRODUCTS=10` |
| **H10-공유** | 해피, 상품 하나 | 1 | 10 | 10 | 10 | 동시 | 10 / 0 | `-e ORDERS=10 -e STOCK=10` |
| **C10-분산** | 경합, 상품마다 2건 | 5 | 1 | 10 | 2 | 동시 | 5 / 5 | `-e ORDERS=10 -e STOCK=1 -e PRODUCTS=5` |
| **C10-집중** | 경합, 상품 하나 | 1 | 1 | 10 | 10 | 동시 | 1 / 9 | `-e ORDERS=10 -e STOCK=1` |
| **H200-분산** | 해피, 상품 나눔 | 200 | 1 | 200 | 1 | 동시 | 200 / 0 | `-e ORDERS=200 -e STOCK=1 -e PRODUCTS=200` |
| **H200-공유** | 해피, 상품 하나 | 1 | 200 | 200 | 200 | 동시 | 200 / 0 | `-e ORDERS=200 -e STOCK=200` |
| **C200-분산** | 경합, 상품마다 2건 | 100 | 1 | 200 | 2 | 동시 | 100 / 100 | `-e ORDERS=200 -e STOCK=1 -e PRODUCTS=100` |
| **C200-집중** | 경합, 상품 하나 | 1 | 1 | 200 | 200 | 동시 | 1 / 199 | `-e ORDERS=200 -e STOCK=1` |

- 실행 명령: `k6 run <k6 옵션> k6/stock-contention.js`. 측정은 위 표 순서대로 한다. (세 버전 모두 같은 순서)
- 코드 읽는 법: H = 해피(전부 성공), C = 경합(재고보다 요청이 많음), L = 진 요청(Loser) 단건. 숫자 = 승인 요청 수. 분산 = 요청이 여러 상품에 나뉨, 공유·집중 = 모든 요청이 상품 하나에 몰림.

| 코드 | 확인할 것 |
|---|---|
| H1 | 이긴 요청 단건 기준선. 동시성 없이 이긴 요청 경로 자체의 비용 |
| L1 | 진 요청 단건 기준선. 두 번째 요청이 동시성 없이 진 요청 경로를 탄다 |
| C2 | 가장 작은 동시 경합 |
| H10-분산 | 동시 요청이 커넥션 풀 크기(10) 이하면 커넥션 대기가 0인가 |
| H10-공유 | H10-분산과의 차이 = 풀 대기가 없을 때의 상품 행 락 비용 |
| C10-분산 / C10-집중 | 같은 10건 경합에서 경합이 흩어진 경우 vs 인기 상품 하나에 몰린 경우 |
| H200-분산 | 풀이 꽉 찼을 때 커넥션 대기만의 비용 (상품 행 경합 없음) |
| H200-공유 | H200-분산과의 차이 = 풀이 꽉 찼을 때의 상품 행 락 비용. 이전 2-4·2-8·2-9와 같은 조건 |
| C200-분산 / C200-집중 | 풀이 꽉 찬 상태에서 흩어진 경합 vs 인기 상품 하나 |

**트랜잭션 수 실측 (별도 실행)**

| ID | 내용 | 조건 |
|---|---|---|
| T1 | H1 + L1을 SQL 로그·Hibernate 세션 통계·트랜잭션 로그를 켜고 한 번씩 | 이전 2-1과 같은 방식. PG 지연 0. 시간 측정과 섞지 않는다 (로그가 시간을 왜곡) |

- 예상 트랜잭션 수: 이긴 요청 X 4 / A 4 / B 2, 진 요청 X 5 / A 3 / B 1. B는 아직 실측한 적이 없다.

- **A의 효과는 경합에서 확실하다.** 진 요청 응답이 655~792ms → 18~230ms, PG 호출이 진 요청 수만큼 → 0. 이것은 시나리오마다 같은 방향이다.
- **A는 상품 하나에 몰린 해피 케이스(H200-공유)도 빠르게 했다.** 701 → 588ms. X에서는 상품 행을 PG 뒤 `complete`에서 잡아 `complete` 135 + `succeed` 135ms를 기다렸다. A는 같은 대기를 PG 앞으로 옮겼고 합이 줄었다.
- **상품 행 경합이 없으면(H200-분산) X와 A는 거의 같다** (490 / 480). 둘 다 트랜잭션 4번이다. B만 커넥션 대기가 절반이 된다.
- **B가 커넥션 대기를 절반으로 줄이는지는 재고 경합이 아니라 "상품 행 하나에 몰리느냐"로 갈린다.** 재고 경합이 있는 C200-분산(상품마다 2건)에서도 A → B가 성공 111 → 53, 실패 211 → 106ms로 절반이다.

| A → B 커넥션 대기 | 재고 경합 없음 | 재고 경합 있음 |
|---|---|---|
| 상품 행에 몰리지 않음 | H200-분산: 155 → 76 (절반) | C200-분산: 111 → 53 (절반) |
| 상품 행 하나에 몰림 | H200-공유: 252 → 255 (같음) | C200-집중: 0 → 140 (나빠짐) |
- **C200-집중 이긴 요청은 X·A가 빠르고 B만 느리다.** (1-8-A 해석 참고)

**해석 (확인하지 않음)**
- 세 버전을 한 줄로 정리하면: **A는 "재고 경합 비용(PG 낭비, 진 요청 지연)"을 없앴고, B는 "요청이 상품 행 하나에 몰리지 않을 때의 커넥션 대기"를 절반으로 줄였다.** (재고 경합 유무와 상관없음) 서로 다른 비용을 줄였다. 상품 행 하나에 몰리면 B의 효과는 사라지고, 재고 경합까지 겹치면(C200-집중) 손해를 봤다.
- H200-공유에서 X가 A보다 느린 이유로 보이는 것: X는 PG에서 돌아온 200건이 한꺼번에 `complete`(상품 행 락)로 몰린다. A는 요청이 들어오는 대로 `startPaying`에서 상품 행을 지나가서, 한꺼번에 몰리는 순간이 없다.

### 1-8-T1. 트랜잭션·SQL 수 실측 (2026-11-23)

**조건:** X(`2f25076`)·A(`5e7823f`)는 worktree, B는 `49f0371`(B 측정 이후 `src/` 변경 없음). 각 버전 DB(`payment_x`/`payment_a`/`payment_b`). PG 지연 0, SQL 로그(`org.hibernate.SQL=debug`), Hibernate 세션 통계, `JpaTransactionManager=debug`. 시간은 재지 않았다.
**방법:** `zsh k6/t1-single.sh <서버 로그> <결과 폴더>`로 H1을 2회, L1(같은 상품에 주문 2건 순차)을 2회 보내고, 승인 요청 1건 동안의 서버 로그만 잘라 `python3 -I k6/t1_summary.py <결과 폴더>`로 집계했다. 요청 스레드의 로그만 본다.
**확인:** 세 버전 모두 1회차와 2회차가 같다. (첫 요청에 초기화 쿼리가 섞이지 않았다) 모든 트랜잭션에서 SQL 로그 수 = Hibernate 통계의 실행 문장 수, 커넥션 획득은 트랜잭션당 1회.

| | 이긴 요청: 트랜잭션 / SQL | 진 요청: 트랜잭션 / SQL | 진 요청에서 롤백된 트랜잭션 |
|---|---|---|---|
| X | 4 / 12 | 5 / 12 | `complete` (재고 부족) |
| A | 4 / 12 | 3 / 7 | `startPaying` (재고 부족) |
| B | **2 / 10** | **1 / 5** | 없음 (실패 기록 후 커밋) |

추정치(이긴 요청 X 4 / A 4 / B 2, 진 요청 X 5 / A 3 / B 1)가 모두 맞았다.

**트랜잭션별 SQL** (`[락]` = 상품 행 `FOR UPDATE`부터 커밋·롤백까지 나간 SQL. UPDATE는 커밋 직전 flush에서 나간다)

X — 이긴 요청
1. `begin` 커밋: SELECT orders FOR UPDATE → SELECT idempotency_key → INSERT idempotency_key
2. `startPaying` 커밋: SELECT orders FOR UPDATE → UPDATE orders
3. `complete` 커밋: SELECT orders FOR UPDATE → INSERT payment → SELECT product FOR UPDATE → UPDATE orders `[락]` → UPDATE product `[락]`
4. `succeed` 커밋: SELECT idempotency_key → UPDATE idempotency_key

X — 진 요청: 1·2는 같음 → 3. `complete` **롤백**: SELECT orders FOR UPDATE → INSERT payment → SELECT product FOR UPDATE (재고 부족, INSERT도 롤백) → (PG 취소) → 4. `revertToPending` 커밋: SELECT orders FOR UPDATE → UPDATE orders → 5. `fail` 커밋: SELECT idempotency_key → UPDATE idempotency_key

A — 이긴 요청
1. `begin` 커밋: X와 같음
2. `startPaying` 커밋: SELECT orders FOR UPDATE → SELECT product FOR UPDATE → UPDATE orders `[락]` → UPDATE product `[락]`
3. `complete` 커밋: SELECT orders FOR UPDATE → INSERT payment → UPDATE orders
4. `succeed` 커밋: X와 같음

A — 진 요청: 1. `begin` 커밋 → 2. `startPaying` **롤백**: SELECT orders FOR UPDATE → SELECT product FOR UPDATE (재고 부족) → 3. `fail` 커밋: SELECT idempotency_key → UPDATE idempotency_key

B — 이긴 요청
1. `startPaying` 커밋: SELECT payment (멱등키) → SELECT orders FOR UPDATE → SELECT product FOR UPDATE → INSERT payment `[락]` → UPDATE orders `[락]` → UPDATE product `[락]`
2. `complete` 커밋: SELECT orders FOR UPDATE → SELECT payment → UPDATE orders → UPDATE payment

B — 진 요청
1. `startPaying` **커밋**: SELECT payment (멱등키) → SELECT orders FOR UPDATE → SELECT product FOR UPDATE → INSERT payment `[락]` (FAILED) → UPDATE orders `[락]` (FAILED)

**확인한 것**
- **상품 행 락을 쥔 채 나가는 SQL:** 진 요청 기준 X 0개(바로 롤백), A **0개(바로 롤백)**, B **2개(INSERT payment, UPDATE orders) + COMMIT**. 1-8-A에서 추정한 "B의 진 요청은 상품 행을 잠근 채 실패 기록을 쓰고 커밋한다"가 SQL로 확인됐다. C200-집중에서 B만 진 요청이 한 줄로 2ms 간격으로 끝난 것(로그 타임스탬프)과 맞는다.
- 이긴 요청도 B는 상품 행 락 안에서 INSERT payment가 하나 더 나간다. (A는 UPDATE 2개, B는 INSERT 1 + UPDATE 2) A의 INSERT payment는 PG 뒤 `complete`에 있다.
- X의 진 요청은 `complete`에서 INSERT payment를 보낸 뒤 롤백한다. (IDENTITY라 즉시 INSERT, granularity 2-1에서 본 "결제 ID가 비는" 원인)
- B는 SQL 수가 크게 줄지 않았다. 이긴 요청 12 → 10개. 트랜잭션 수(4 → 2)만큼 줄어든 것은 커넥션 획득·BEGIN·COMMIT 왕복이다.

**해석 (확인하지 않음)**
- C200-집중의 B 손해를 줄이려면 진 요청이 상품 행 락을 쥔 구간에서 쓰기와 커밋을 빼야 한다. (예: 재고 확인 전에 실패 기록 대상을 정해 두고, 상품 행은 마지막에 잠그거나, 품절 상품은 락 전에 거절) 개선이므로 지시 전까지 적용하지 않는다.
