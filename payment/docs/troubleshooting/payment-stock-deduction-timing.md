# 결제 승인: 재고 차감 시점과 경합 시 보상 취소 폭증

> 상태: **현재 구조 재현 완료, 개선 미적용** (phase-04 진행 중, 현재 결제 구조를 "설계 실패 버전"으로 보고 정리한 문서)
> 2-1은 동시성 테스트로 재현했다. (7번 결과) 2-2, 2-3은 아직 코드를 읽고 추론한 것이다.

---

## 1. 배경

결제 승인은 `PaymentFacade.approve()`가 트랜잭션 없이 아래 순서로 오케스트레이션한다. (ARCHITECTURE 5-2: 선 외부 I/O → 후 DB 트랜잭션)

```
1. startPaying  (짧은 트랜잭션)  주문 선점 PENDING → PAYING
2. PG 승인 호출 (트랜잭션 밖)
3. complete     (짧은 트랜잭션)  Order PAID + Payment 저장 + 재고 차감
4. 3번 실패 시                   PG 승인 취소(보상) 후 PAYING → PENDING
```

- 재고는 **3번, PG 승인이 끝난 뒤**에 차감한다. (`PessimisticLockPaymentStateService.complete()`)
- 주문 생성(`Order.create()`)은 재고를 차감하지 않고 `stock >= quantity`만 사전 확인한다.
- 이 시점은 phase-03 "시작 전에 정할 것"(`주문 생성 시 선점 vs 결제 승인 시 차감`)에서 결정한 것이다.

## 2. 문제 (가설)

### 2-1. 경합에서 진 요청도 전부 PG 승인까지 간다
재고 1개인 상품에 주문 N건(각 수량 1)이 동시에 승인되면:

| 단계 | 일어나는 일 |
|---|---|
| startPaying | 주문이 서로 다르므로 N건 모두 선점 성공 (재고를 보지 않음) |
| PG 승인 | **N건 모두 승인** (돈이 N번 나감) |
| complete | 상품 행 락에서 줄을 서서 1건만 차감 성공, N-1건은 재고 부족 |
| 보상 | **N-1건 PG 승인 취소** 후 `PENDING` 복구 |

- 사용자 N-1명은 "결제됐다가 환불"을 겪는다. (카드 승인 알림, 환불 지연)
- HTTP 응답은 200 1건, 409(`STATE_CONFLICT`) N-1건이다. **응답만 보면 정상적인 경합 실패처럼 보이고, 뒤에서 일어난 PG 왕복 2(N-1)번은 드러나지 않는다.**

### 2-2. 보상 취소 자체가 실패할 수 있다
- PG 취소는 외부 I/O라 실패·타임아웃이 날 수 있다.
- 취소가 실패하면 주문은 `PAYING`, 돈은 나간 상태로 남는다. (`PaymentFacade.compensate()`)
- 경합 수만큼 보상 시도가 생기므로, 이런 미아 주문도 경합 수에 비례해 늘어난다.

### 2-3. 진 주문이 다시 결제를 시도할 수 있다
- 보상 후 주문은 `PENDING`으로 돌아간다. `startPaying`은 재고를 보지 않으므로, 재고가 0이어도 다시 PG 승인까지 간다.
- 재시도할 때마다 승인 → 취소가 반복될 수 있다.

## 3. 원인: 왜 뒤에 뒀나

당시 판단의 근거로 추정되는 것:

1. **결과를 모르는 상태에 재고를 묶지 않으려고.** PG 전에 빼면 PG 타임아웃 시 재고를 돌려줄지 확정할지 알 수 없어 재고가 `PAYING`에 묶인다.
2. **흔한 실패에 보상을 붙이지 않으려고.** 결제 실패(결제창 이탈, 카드 거절)는 흔하고 재고 부족은 드물다고 봤다. 그러면 흔한 실패마다 재고 복구가 붙는 것보다, 드문 실패에만 PG 취소가 붙는 쪽이 낫다.

> 처음에는 "재고 행 락을 PG 호출 동안 쥐지 않으려고"도 이유로 들었지만, 이건 근거가 아니다.
> PG 호출은 어느 쪽이든 트랜잭션 밖이므로, 재고를 `startPaying`에서 빼든 `complete`에서 빼든 락은 짧은 트랜잭션 안에서만 쥔다.
> 원자성도 같다. 앞에 두면 `PENDING → PAYING` 전이와 차감이 한 트랜잭션으로 묶이고, 불변식이 "PAID 수량 = 차감 재고"에서 "PAYING + PAID 수량 = 차감 재고"로 바뀔 뿐이다.

**실패한 지점:** 2번은 "재고 부족은 드물다"는 전제 위에 있다. 그런데 이 서비스의 주제가 "동시 주문이 몰려 재고가 부족해지는 상황"이다. (intent 5번, phase-02)
경합이 심하면 드물어야 할 실패가 흔해져, **보상 취소가 경합 수만큼 발생한다.** 일반 커머스에서는 맞는 선택이 선착순·한정 수량 상황에서 뒤집혔다.

## 4. 개선 후보: 재고 차감을 PG 호출 앞(`startPaying`)으로

`startPaying` 트랜잭션에서 `PENDING → PAYING` 전이와 재고 차감을 함께 한다.
"주문 생성 시 선점"과는 다르다. 사용자가 결제창 인증까지 마치고 승인을 요청한 시점이라, 결제하지 않고 떠난 주문이 재고를 붙잡지 않고 선점 만료 스케줄러도 필요 없다.

| | 앞에 둘 때 (재고 복구) | 뒤에 둘 때 (PG 취소) — 현재 |
|---|---|---|
| 보상이 일어나는 때 | PG 거절 때마다 (흔함) | 재고 부족 때마다 (경합이 적으면 드묾, 많으면 흔함) |
| 보상 내용 | 우리 DB에서 `stock + n` | 외부 PG 취소 API 호출 |
| 보상 실패 가능성 | 상태 복구와 같은 트랜잭션이라 함께 성공·롤백 | 타임아웃·취소 실패 → 또 다른 "모름" 상태 |
| 사용자 영향 | 없음 | 결제됐다가 환불됨 |
| 경합에서 진 요청 | PG 호출 전에 탈락 | PG 승인 + 취소 왕복 후 탈락 |
| 타임아웃 시 | 결과를 모르는 동안 그 수량을 못 판다 (타임아웃은 드물고 4-4 대사로 풀림) | 재고 영향 없음 |
| 추가 코드 | `PAYING`에서 빠져나가는 모든 경로(거절, 연동 오류, 보상 성공, 대사 미승인)에서 재고 복구 | 없음 |

**판단 기준: 재고의 양이 아니라 "재고 대비 동시 수요"**
- 경합이 거의 없으면 어느 쪽이든 문제가 드러나지 않는다. 뒤에 두는 것도 받아들일 만하다.
- 경합이 있으면 앞에 둬야 한다.
- 애매하면 앞이 안전하다. 잃는 것(DB 복구 코드)은 우리가 통제할 수 있는 비용이고, 뒤의 보상(PG 취소)은 드물어도 비싸고 그 자체가 실패할 수 있다.

## 5. 재현 계획

### 5-1. JUnit 동시성 테스트 (증명용)
`PaymentFlowTestSupport`에 추가해 비관적 락·원자적 쿼리 구현체 모두에서 같은 시나리오로 돌린다.
기존 `dbFailureThenCompensate()`는 `setStock()`으로 재고를 줄여 흉내 낸 **단일 스레드 버전**이라, 경합 수에 비례한다는 것은 보여주지 못한다.

- given: 재고 1, 서로 다른 주문 N건(각 수량 1)
- when: `ExecutorService` + `CountDownLatch`로 N건 동시 `paymentFacade.approve()`
- then:

| 검증 항목 | 현재 구조 기대값 | 개선 후 기대값 |
|---|---|---|
| 성공 / 실패 | 1 / N-1 | 1 / N-1 |
| `approveCallCount` | **N** | **1** |
| `cancelCallCount` | **N-1** | **0** |
| 최종 재고 | 0 | 0 |
| 실패 주문 상태 | `PENDING` (승인 후 취소를 거쳐 복구) | `PENDING` (선점 트랜잭션이 롤백되어 그대로) |
| 소요 시간 | 로그 | 로그 |

변형:
- `fakePaymentClient.delay(...)`: 진 요청이 PG 왕복만큼 시간을 쓰는 것을 소요 시간으로 확인
- `fakePaymentClient.willFailCancel()`: `PAYING`에 갇히는 주문이 N-1건으로 늘어나는 것을 확인

### 5-2. k6 부하 테스트 (체감용, 선택)
- fake 모드(`app.pg.provider` 기본값)로 서버를 띄우고 `POST /api/orders` N건 → 승인 N건을 동시에 보낸다.
- 실제 토스로는 할 수 없다. `paymentKey`를 주문마다 결제창에서 받아야 하고, `cancel()`이 아직 미구현이다. (4-3)
- **주의: HTTP 응답만으로는 현재와 개선 후가 같아 보인다.** PG 호출 횟수를 셀 수단이 필요하다.
  - 현재 셀 수 있는 것: 보상마다 찍히는 `PG 승인 후 결제 반영 실패. 승인 취소를 시도한다` warn 로그 줄 수
  - 대안: actuator 카운터, fake 전용 조회 API (둘 다 미구현)
- `FakePaymentClient.delay()`는 코드에서만 설정할 수 있다. k6에서 지연 효과를 보려면 프로퍼티로 설정하게 바꿔야 한다.

> **실패한 요청이 성공한 요청보다 약 2배 느리다.** 성공은 PG 승인 1번(300ms), 실패는 승인 + 보상 취소 2번(600ms)을 거치기 때문으로 보인다. 실패 최소값(726ms)도 600ms를 넘는다.
> 즉 "재고가 없어서 거절"이라는 결과를 받기까지, 경합에서 진 사용자가 가장 오래 기다린다. 그동안 요청 스레드도 붙잡혀 있다.
> 600ms를 넘는 나머지(약 130~230ms)는 상품 행 락 대기와 보상 트랜잭션으로 추정한다. 이 부분은 분해해서 확인하지 않았다.
> 단발 측정이다. PG 호출 횟수(100/99)는 결정적이고, 응답 시간은 대략적인 비교로만 본다.

## 8. 학습 포인트

- **내 문제를 남에게 전파하지 말라.** 재고 부족은 우리 문제인데, 뒤에서 판정하면 PG(승인 후 취소)와 사용자(결제 후 환불)에게 번진다. 앞에서 판정하면 DB 트랜잭션 안에서 끝난다. 반대로 PG 거절이라는 바깥 문제는 우리 DB 복구로 조용히 흡수한다.
- 일반화하면: **되돌리기 어려운 외부 작업(돈, 메일, 외부 API) 전에, 우리 쪽에서 실패할 수 있는 건 전부 먼저 실패시킨다.** PG 호출 뒤에 남는 실패는 "PG 결과를 모름"처럼 바깥에서 오는 것뿐이어야 한다.
- 설계 선택에는 전제가 있다. "재고 부족은 드물다"는 전제는 일반 커머스에서는 맞고, 경합이 주제인 이 서비스에서는 틀렸다.
- 테스트 대역은 비용을 숨길 수 있다. 가짜 PG의 취소는 항상 즉시 성공하므로, 실제 보상 비용(지연, 취소 실패)을 과소평가한다.
