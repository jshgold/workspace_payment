# 락 전략 비교 (phase-02)

> 이 문서의 **측정값, 표 틀, 장단점(실험에서 확인한 사실)은 Claude가 채웠고, `적합성 판단`·`결론`·`선택 이유`는 직접 작성**합니다.
> 비어 있는 칸은 `(직접 작성)`으로 표시해 두었습니다.

## 1. 실험 조건

- 공통 실험: 상품 1개에 스레드 100개가 동시에 1개씩 차감 (`StockConcurrencyTestSupport`)
  - 시나리오 A: 초기 재고 100 → 성공 100, 최종 재고 0이어야 함
  - 시나리오 B: 초기 재고 50 → 성공 50, 실패 50, 최종 재고 0이어야 함
- 환경: 로컬 Docker (Testcontainers MySQL 8.0 / Redis 7), Hikari 기본 풀(10), 단일 실행 1회
- **정상 판정식:** `성공 건수 × 수량 + 최종 재고 == 초기 재고`
- 주의: 소요 시간은 단일 실행값이고 수십 ms 차이는 실행마다 달라집니다. 작은 차이로 우열을 단정하지 말고 **경향**만 보세요.
- 다시 측정하기:
  ```
  ./gradlew cleanTest test --tests "*StockDecreaseServiceTest" --tests "*StockDecreaseFacadeTest" --console=plain -i
  ```
  로그에서 `→ 성공` 줄을 찾으면 됩니다.

## 3. 전략별 장단점

장점·단점은 이번 실험에서 확인한 사실 위주입니다. 숫자는 시나리오 A(재고 100 / 요청 100) 기준 단일 실행값이고, "이론상"이라고 표시한 것은 실험으로 확인하지 않은 일반론입니다.
**이 서비스에서의 적합성은 직접 작성하는 칸**입니다.

| 전략 | 장점 | 단점 | 이 서비스에서의 적합성 |
|---|---|---|---|
| 1. 락 없음 | 구현이 가장 단순하고 락 오버헤드가 없다 (111ms) | Lost Update 발생. 재고 100에서 성공 100건인데 최종 재고 90, 재고 50에서 100건 성공(초과 판매). 운영에 쓸 수 없고 비교 기준선 용도 | 부적합. 문제를 재현하는 기준선으로만 의미가 있다 |
| 2. 조건부 Atomic Update | 조회 없이 UPDATE 한 문장으로 확인+차감+SOLD_OUT 전환. 커넥션 1개, 락 대기 코드 없음 (118ms). 실패는 영향 행 수 0으로 판단 | 도메인 규칙이 SQL로 새어 나가 `Product.decreaseStock`과 쿼리에 이중으로 관리됨. SOLD_OUT 판정이 MySQL의 SET 평가 순서에 의존. 벌크 연산이라 영속성 컨텍스트와 불일치(`clearAutomatically` 필요). `@Version`을 올리지 않음 | 차선책(초안). 정합성과 속도는 좋지만 규칙이 두 곳에 있는 부담이 있다. 같은 행에 요청이 몰리는 핫스팟에서 우선 검토할 후보 |
| 3. 비관적 락 | 도메인 메서드를 그대로 재사용해 규칙이 한 곳에 있음. 추가 인프라 없이 DB만으로 해결. 속도는 Atomic과 비슷한 수준 (140ms) | 행 락이 트랜잭션 끝까지 유지되어 락 시간이 트랜잭션 길이에 비례함. 락 대기 타임아웃(3초) 설정 필요. 이론상 여러 행을 서로 반대 순서로 잠그면 데드락 가능 (이 프로젝트는 주문당 상품 1개라 해당 가능성이 작음) | **선택(초안).** 규칙이 한 곳에 있고, 단일 MySQL에서 추가 인프라 없이 정합성을 지키며, 속도도 Atomic과 큰 차이가 없었다 |
| 4. 낙관적 락 | 락 대기가 없고, 충돌이 드문 데이터에는 가벼움 | 충돌이 많은 재고 차감에서 재시도 폭증 (요청 100에 약 500회, 383ms로 Atomic의 약 3배). 재시도 로직을 트랜잭션 바깥(Facade)에 둬야 함. 재시도 한도를 넘으면 재고가 있어도 실패. `@Version`이 엔티티 전체에 영향을 줘서 다른 전략의 기준선까지 바꿈 | 재고 차감에는 부적합. 충돌이 드문 데이터(상품 정보 수정 등)에는 적합 |
| 5. MySQL Named Lock | 행이 없거나 여러 행을 묶어 잠가야 할 때도 이름으로 잠글 수 있음. 별도 인프라 없이 같은 DB를 쓰는 여러 앱 서버 사이에서 동작 (247ms) | 한 요청이 커넥션 2개를 점유함. 비즈니스 풀을 공유하면 풀 고갈로 성공이 7~9건에 그침 → 락 전용 풀 분리 필요. 락은 커밋이 아니라 `RELEASE_LOCK`이나 세션 종료로 풀려서 해제 누락/실패 시 락이 세션에 남음 | 부적합. 단일 행 재고에는 커넥션 이중 점유 비용만 더 든다. 행이 없는 대상을 직렬화해야 하는 특수한 경우용 |
| 6. Redis 분산 락 (Redisson) | DB 커넥션을 쓰지 않아 풀 데드락이 구조적으로 없음. 여러 서버, DB 밖 자원까지 같은 락으로 묶을 수 있음. 재진입, 자동 연장(watchdog), Pub/Sub 대기 제공 (230ms) | Redis 인프라가 추가됨. 락과 DB 트랜잭션이 별개 시스템이라 순서(락 → 트랜잭션 → 커밋 → 해제)를 코드가 보장해야 함. 로직이 `leaseTime`을 넘기면 상호 배제가 깨짐(실험으로 확인). Redis 장애/failover 때 락 유실은 미검증 | 현재는 과함. 락 저장소를 DB와 분리해야 할 때(여러 DB, 외부 연동 포함 작업)의 후보 |
| 6'. Redis 스핀락 | 의존성이 작고 `SET NX PX`와 Lua 두 가지만으로 구현됨. 동작 원리가 투명함 | 폴링 (`SET NX` 약 930회, 386ms로 Redisson보다 느림). 락이 풀려도 다음 폴링까지 대기자가 모름. 공정성, 재진입, 자동 연장이 없음. 소유자 토큰 확인 없이 해제하면 남의 락이 지워짐(실험으로 확인). `leaseTime` 초과 시 상호 배제가 깨지는 점은 Redisson과 같음 | 비추천. Redisson을 쓸 수 있다면 직접 만들 이유가 거의 없다. 락의 동작 원리를 배우는 용도 |

## 4. 실험에서 겪은 사실 (정리 재료)

결론이 아니라 **실제로 일어난 일의 기록**입니다. 장단점과 결론을 쓸 때 근거로 쓰세요.

- **`@Version` 추가가 락 없음 기준선을 깼다 (2-5).** 같은 엔티티에 낙관적 락용 컬럼을 넣자 더티 체킹 UPDATE에 `AND version=?`가 붙어 락 없음도 낙관적 락으로 동작했고, Lost Update 재현 테스트가 실패했다. 락 없음 서비스를 `version` 검사가 없는 벌크 UPDATE로 바꿔 재현을 되살렸다.
- **Atomic Update는 `@Version`을 올리지 않는다.** 직접 쓴 UPDATE 쿼리는 Hibernate를 거치지 않아서, 같은 행을 낙관적 락과 섞어 쓰면 충돌 감지에 구멍이 생긴다. (이번엔 전략별로 따로 돌려서 영향 없음)
- **낙관적 락은 충돌이 많으면 재시도가 폭증한다.** 요청 100개에 재시도 약 500회(시나리오 A). 재시도는 트랜잭션 바깥(Facade)에서 해야 하고, 시도마다 새 트랜잭션·새 조회가 필요하다.
- **Named Lock은 한 요청이 DB 커넥션을 2개 쓴다.** 락을 잡은 커넥션과 트랜잭션 커넥션이 다르다. 비즈니스 풀을 공유하면 풀 고갈로 성공이 7~9건에 그쳤다. 락 전용 풀을 분리하면 데드락은 구조적으로 없어지고, 풀이 모자라면 느려지거나 타임아웃이 난다.
- **Named Lock은 테이블에 기록되지 않는다.** MySQL 서버 메모리의 락이고, 트랜잭션 커밋이 아니라 `RELEASE_LOCK`이나 세션 종료로 풀린다. 해제 실패 시 그 커넥션은 풀에서 버려야 한다.
- **Redisson `leaseTime`을 로직이 넘기면 상호 배제가 깨진다.** 임계구역에 2개 이상이 동시에 들어가는 것을 확인했고, 해제 시점에는 이미 내 락이 아니라서 `isHeldByCurrentThread()` 확인이 필요했다.
- **스핀락의 소유자 토큰 확인은 필수다.** 토큰 없이 DEL로 풀면 만료 후 다른 스레드가 얻은 락을 지워서 세 번째 스레드가 동시에 들어왔다. Lua로 확인-삭제를 원자적으로 해야 막힌다.
- **예상과 달랐던 측정:** Redisson이 스핀락보다 Redis 명령을 더 많이 썼다(약 2100건 대 약 1100~1230건). 이 조건(대기자 100, 임계구역 수 ms)에서는 "Pub/Sub이 폴링보다 요청이 적다"가 성립하지 않았다. 원인은 검증하지 않은 가설 단계다. 스핀락 간격은 `app.redis.spin.min-interval-ms` / `max-interval-ms`로 바꿔 다시 측정할 수 있다.
- **Redis 락은 DB와 별개 시스템이다.** 락 순서(락 → 트랜잭션 → 커밋 → 해제)는 코드(Facade)가 보장해야 하고, Redis 장애/failover 시 락 유실은 이 실험에서 다루지 않았다.

## 5. 결론

> **Claude가 작성한 초안입니다.** 사용자가 대화에서 한 판단을 근거로 정리했으니, 직접 읽고 동의하지 않는 부분은 고쳐서 확정하세요.
> 면접에서 말할 때는 본인이 납득한 문장으로 바꿔야 합니다.

### 이 서비스(단일 MySQL, 재고 차감)라면 어떤 락을 쓰겠는가?

**비관적 락(`PESSIMISTIC_WRITE`)**을 기본으로 쓴다. 같은 행에 요청이 크게 몰리는 상품이 생기면 **조건부 Atomic Update**로 옮기는 것을 검토한다.

### 선택한 이유 (측정값과 위 사실을 근거로)

1. **정합성으로는 변별되지 않았다.** 정상 구성의 전략(Atomic, 비관적, 낙관적, Named Lock, Redis)은 모두 공통 실험 조건을 통과했다. 깨진 것은 락 없음뿐이었다. 정합성은 "락이 있느냐"의 문제였고 "어떤 락이냐"의 기준이 되지 못했다.
2. **속도로도 갈리지 않았다.** 시나리오 A에서 Atomic 118ms, 비관적 140ms, 시나리오 B에서 171ms와 99ms로 순서가 뒤집혔다. 단일 실행이고 임계구역이 짧은 실험이라 큰 차이를 측정하지 못했다. 이 실험만으로는 "Atomic이 더 빠르니 Atomic"이라고 말할 근거가 약하다.
3. **규칙이 한 곳에 있다.** 비관적 락은 `Product.decreaseStock`을 그대로 재사용한다. Atomic Update는 삭제·판매중지·재고 부족 검사와 SOLD_OUT 전환이 JPQL에 다시 들어가고, SOLD_OUT 판정은 MySQL의 SET 평가 순서에 의존한다. 이 중복은 phase-03의 결제 취소(재고 복구)에서 복구 규칙이 SQL로 하나 더 생기면서 커진다. 규칙이 바뀔 때 고칠 곳이 늘어나고, 한쪽만 고치면 조용히 어긋난다.
4. **추가 인프라와 커넥션 비용이 없다.** Named Lock은 한 요청이 커넥션 2개를 점유해서 풀 고갈 위험이 있었고(공유 풀에서 성공 7~9건), 락 전용 풀을 따로 둬야 했다. Redis 락은 단일 DB의 단일 행 재고에는 과하고 인프라가 하나 더 늘어난다. 낙관적 락은 재고처럼 충돌이 많은 곳에서 재시도가 폭증했다(요청 100에 약 500회).
5. **비관적 락의 위험이 현재 범위에서는 작다.** 주문당 상품이 1개라서 여러 행을 반대 순서로 잠그는 데드락이 생기지 않는다. 락 대기 타임아웃(3초)은 설정해 둔다.

**이 선택을 지키기 위한 조건:** 비관적 락은 락이 트랜잭션 끝까지 유지되므로, 락을 쥔 구간에는 재고 차감만 넣는다. **결제처럼 오래 걸리는 외부 호출은 트랜잭션 밖(Facade)에서 처리한다.** (ARCHITECTURE 4~5번) 이 조건이 깨지면 같은 상품의 다른 주문이 전부 줄을 서게 된다.

### 선택하지 않은 전략과 그 이유

- **락 없음:** Lost Update가 발생한다 (재고 100에서 성공 100건인데 최종 재고 90, 재고 50에서 100건 성공). 비교 기준선으로만 의미가 있다.
- **조건부 Atomic Update:** 정합성과 속도는 좋았다. 규칙의 이중 관리와 MySQL 평가 순서 의존, 영속성 컨텍스트 불일치 때문에 차선책으로 뒀다. 핫스팟 대응이 필요해지면 가장 먼저 검토한다.
- **낙관적 락:** 충돌이 많은 재고에서 재시도가 폭증했고, 한도를 넘으면 재고가 있어도 실패한다. `@Version`이 엔티티 전체에 영향을 줘서 다른 전략의 기준선까지 바꿨다.
- **MySQL Named Lock:** 한 요청이 커넥션 2개를 쓴다. 풀을 공유하면 풀 고갈, 분리해도 해제 누락 위험이 남는다. 단일 행 재고에는 얻는 것이 없다.
- **Redis 분산 락(Redisson):** 단일 DB 재고에는 과하다. 인프라가 늘고, 락과 DB 트랜잭션이 별개 시스템이라 순서와 `leaseTime`을 직접 관리해야 한다.
- **Redis 스핀락:** Redisson이 있다면 직접 만들 이유가 거의 없다. 폴링 부하, 락 해제 후 반응 지연, 소유자 토큰 처리 같은 것을 직접 챙겨야 한다.

### 요구사항이 바뀐다면? (예: 서버 여러 대, 외부 결제 API 연동, 선착순 이벤트)

| 바뀌는 요구사항 | 선택은? | 이유와 주의점 |
|---|---|---|
| **앱 서버가 여러 대로 늘어난다** (DB는 그대로 단일 MySQL) | **그대로 비관적 락** | `SELECT ... FOR UPDATE`는 앱 서버가 아니라 DB가 직렬화한다. 서버 수와 무관하게 유효하다. 서버가 늘었다고 분산 락이 필요해지는 것이 아니다 |
| **선착순 이벤트 등으로 한 상품에 요청이 폭주한다** | **조건부 Atomic Update로 전환 검토** | 조회와 차감이 UPDATE 한 문장이라 락을 쥔 구간과 DB 왕복이 줄어든다. 규칙의 이중 관리는 "도메인 메서드와 쿼리가 같은 입력에서 같은 결과를 내는지" 테스트로 묶어 줄인다. 그래도 한 행에 쏠리는 병목은 남으므로, 그 이상은 재고를 나누거나 큐잉으로 푸는 별도 설계가 필요하다 |
| **결제 PG 연동(phase-03)** | 락 전략은 유지, **트랜잭션 구조를 바꾼다** | 외부 호출을 기다리는 동안 DB 락과 커넥션을 쥐면 안 된다. 짧은 트랜잭션(주문 PENDING 저장 → 커밋) → 트랜잭션 밖에서 PG 호출 → 짧은 트랜잭션(PAID 또는 취소+재고 복구) 순서로 끊고, 실패 시 보상 작업을 둔다. 주문·결제는 유실이 허용되지 않으므로 비동기 적재만으로 처리하지 않고 Outbox를 쓴다 |
| **주문 하나에 여러 상품을 담는다** | 비관적 락 + **잠금 순서 고정** | 상품 여러 행을 서로 다른 순서로 잠그면 데드락이 난다. 상품 id 오름차순으로 잠그도록 순서를 고정한다. 순서 고정이 어렵거나 대상이 행이 아니면 Named Lock / Redis 락으로 묶는 것도 후보 |
| **재고가 DB 밖에 있거나 DB가 여러 개로 나뉜다** (샤딩, 외부 재고 시스템) | **Redisson 분산 락** | DB 락은 같은 DB 안에서만 유효하다. 락 저장소를 DB와 분리해야 한다. 이때 `락 획득 → 트랜잭션 → 커밋 → 락 해제` 순서를 Facade로 보장하고, `leaseTime`을 로직 최대 시간보다 충분히 길게 잡는다(초과하면 상호 배제가 깨짐). 락 유실에 대비해 DB 쪽에도 최종 방어선(조건부 UPDATE나 제약)을 둔다 |
| **충돌이 드문 데이터를 수정한다** (상품 이름·가격 수정 등) | **낙관적 락(`@Version`)** | 락 대기가 없고 가볍다. 재고 차감 경로와는 분리해서 쓴다 |

### 면접 답변 초안 (1분 분량)

"재고 차감의 동시성을 락 없음, 조건부 Atomic Update, 비관적 락, 낙관적 락, MySQL Named Lock, Redis 분산 락 순서로 같은 테스트로 비교했습니다. 락이 없으면 재고 100에 100건이 성공해도 최종 재고가 90으로 남는 Lost Update가 재현됐고, 락을 쓴 전략들은 모두 정합성을 지켰습니다. 정합성과 속도에서는 큰 차이가 나지 않아서, 유지보수와 운영 비용으로 골랐습니다. Atomic Update는 빠르지만 도메인 규칙이 SQL로 새어 나가 규칙을 두 곳에서 관리해야 했고, Named Lock은 한 요청이 커넥션을 두 개 써서 풀을 공유하면 풀 고갈로 성공이 한 자릿수까지 떨어졌습니다. 그래서 단일 DB의 재고 차감에는 도메인 메서드를 그대로 재사용하는 비관적 락을 선택했습니다. 다만 락이 트랜잭션 끝까지 유지되기 때문에 결제 같은 외부 호출은 트랜잭션 밖에서 처리하도록 구조를 나눴습니다. 요구사항이 바뀌면, 서버가 늘어나는 것만으로는 DB 락이 그대로 유효하니 바꾸지 않고, 한 상품에 요청이 폭주하면 Atomic Update로, DB가 여러 개로 나뉘거나 외부 자원까지 묶어야 하면 Redisson 분산 락으로 옮기겠습니다."
