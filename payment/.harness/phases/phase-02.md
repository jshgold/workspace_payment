# Phase 02. 재고 차감과 락 전략 비교

**목표:** 같은 문제(동시 재고 차감)를 6가지 방식으로 풀고, 같은 테스트로 결과를 비교한다.
**이 phase가 프로젝트의 핵심이다.** 각 전략마다 구현 전에 Claude가 방식과 트레이드오프를 먼저 설명하고, 사용자가 이해했는지 확인한 뒤 구현한다.

**공통 실험 조건 (모든 전략에 동일하게 적용)**
- 초기 재고 100, 100개 스레드가 각각 1개씩 차감 → 최종 재고 0이어야 함
- 초기 재고 50, 100개 스레드가 각각 1개씩 차감 → 성공 50, 실패 50, 최종 재고 0이어야 함

---

- [x] **2-1. 재고 차감 도메인 로직과 공통 구조**
  - `Product.decreaseStock(int quantity)`: 재고 부족 시 예외, 0이 되면 `SOLD_OUT`
  - 전략별 구현체를 갈아끼울 수 있는 인터페이스 (예: `StockDecreaseService`)
  - 위 공통 실험 조건을 재사용할 수 있는 동시성 테스트 틀
  - **완료 조건:** 도메인 단위 테스트 통과
  - **학습 포인트:** 왜 전략을 인터페이스로 분리하나? (같은 테스트로 공정하게 비교하기 위해)

- [x] **2-2. 락 없음 — 문제 재현**
  - 조회 → 차감 → 더티 체킹 저장
  - **완료 조건:** 동시성 테스트가 **실패하는 것**을 확인 (최종 재고가 0이 아님)
  - **학습 포인트:** Lost Update가 왜 생기는지 두 트랜잭션의 타임라인으로 그려본다. `synchronized`를 붙이면 왜 해결이 안 되나? (`@Transactional` 프록시와 커밋 시점)

- [x] **2-3. 조건부 Atomic Update**
  - `UPDATE product SET stock = stock - :qty WHERE id = :id AND stock >= :qty`
  - 영향받은 행 수로 성공/실패 판단, `SOLD_OUT` 상태 처리 방법 결정
  - **완료 조건:** 공통 실험 조건 통과
  - **학습 포인트:** 가장 빠르고 단순한데 왜 항상 쓰지 않나? (도메인 로직이 SQL로 새어 나감, 영속성 컨텍스트와 불일치 → `clearAutomatically`)

- [x] **2-4. 비관적 락**
  - `@Lock(PESSIMISTIC_WRITE)` 조회 메서드, 락 타임아웃 힌트
  - **완료 조건:** 공통 실험 조건 통과, SQL 로그에서 `FOR UPDATE` 확인
  - **학습 포인트:** 다른 트랜잭션은 어디서 기다리나? 두 상품을 서로 반대 순서로 잠그면 데드락이 나는지 직접 실험해본다. MySQL `SHOW ENGINE INNODB STATUS`로 데드락 로그 확인.

- [x] **2-5. 낙관적 락**
  - Flyway `V2__add_product_version.sql`로 `version` 컬럼 추가, `@Version`
  - 충돌 시 재시도: 재시도 로직은 트랜잭션 **바깥**(Facade)에 둔다
  - **완료 조건:** 공통 실험 조건 통과, 재시도 횟수와 소요 시간 기록
  - **학습 포인트:** 재시도를 `@Transactional` 메서드 안에서 하면 왜 안 되나? 충돌이 많은 재고 차감에 낙관적 락이 적합한가?

- [x] **2-6. MySQL Named Lock**
  - `GET_LOCK` / `RELEASE_LOCK`, 락 획득 → 트랜잭션 → 해제 순서를 Facade로 보장
  - **완료 조건:** 공통 실험 조건 통과
  - **학습 포인트:** 락을 잡은 커넥션과 비즈니스 트랜잭션 커넥션이 다르면 무슨 일이 생기나? 커넥션 풀 고갈 위험. (ARCHITECTURE 4번 `REQUIRES_NEW` 금지와 연결)

- [x] **2-7. Redis 분산 락 (Redisson)**
  - docker-compose와 Testcontainers에 Redis 추가, Redisson 설정
  - `락 획득 → 트랜잭션 시작 → 로직 → 커밋 → 락 해제` 순서 보장
  - **완료 조건:** 공통 실험 조건 통과
  - **학습 포인트:** 커밋 전에 락을 풀면 무슨 일이 생기나? `waitTime`과 `leaseTime`은 각각 무엇이고, 로직이 `leaseTime`보다 오래 걸리면?

- [ ] **2-7+. Redis 스핀락 (사용자 요청으로 추가한 선택 과제)**
  - Redis `SET key token NX PX leaseTime` + 재시도 루프(sleep)로 직접 구현. Redisson 없이 Lettuce 수준의 명령만 사용
  - 소유자 토큰 확인 후 해제(Lua 스크립트), 락 획득 → 트랜잭션 → 커밋 → 락 해제 순서는 Facade로 보장
  - **완료 조건:** 공통 실험 조건 통과, Redis 요청 수(폴링 횟수)와 소요 시간을 Redisson과 비교해 기록
  - **학습 포인트:** 스핀락은 왜 폴링 부하가 생기나? Redisson은 Pub/Sub으로 이를 어떻게 줄이나? 소유자 토큰 없이 해제하면 무슨 일이 생기나?

- [ ] **2-8. 비교 정리 (사용자가 직접 작성)**
  - `docs/lock-comparison.md`에 전략별 성공 건수, 최종 재고, 소요 시간, 장단점 표 작성
  - Claude는 표 틀과 측정값만 채우고, **결론과 선택 이유는 사용자가 쓴다.**
  - **학습 포인트:** "이 서비스라면 어떤 락을 쓰겠는가"를 근거와 함께 말할 수 있어야 한다. (면접 답변으로 그대로 쓸 수 있게)
