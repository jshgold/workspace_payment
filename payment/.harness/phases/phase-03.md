# Phase 03. 주문·결제

**목표:** 외부 API(PG)가 끼어든 상황에서 트랜잭션과 락 범위를 나누고, 중복 결제를 막는다.
phase-02의 락이 "DB 안의 동시성"이었다면, 여기서는 "외부 시스템이 섞인 동시성"을 다룬다.

**시작 전에 정할 것** (결정 결과는 `intent.md` 8절에 기록)
- PG사 (토스페이먼츠, 포트원 등) — 정하기 전까지는 가짜 PG로 진행
- 재고 차감 시점: 주문 생성 시 선점 vs 결제 승인 시 차감
- 재고 차감에 쓸 락 전략 (phase-02 비교 결과로 결정)

---

- [x] **3-1. Order 엔티티와 주문 생성 API**
  - Flyway로 `orders` 테이블, `Order.create(...)`: 상태 `PENDING`, 금액은 서버에서 계산
  - `POST /api/orders` (`memberId`, `productId`, `quantity`)
  - **완료 조건:** 판매 중이 아닌 상품, 재고 부족 시 주문 실패 테스트
  - **학습 포인트:** 결제 금액을 클라이언트가 보낸 값으로 믿으면 어떤 공격이 가능한가?

- [x] **3-2. PG 클라이언트 추상화와 가짜 PG**
  - `PaymentClient` 인터페이스, 테스트용 `FakePaymentClient` (지연, 실패, 타임아웃 흉내)
  - **완료 조건:** 가짜 PG로 승인/실패/타임아웃 시나리오를 만들 수 있다.
  - **학습 포인트:** 외부 API 응답이 3초 걸릴 때, 그동안 DB 커넥션을 잡고 있으면 어떻게 되나?

- [x] **3-3. 결제 승인**
  - Facade: 외부 PG 승인 → 짧은 트랜잭션(Payment 저장, Order `PAID`, 재고 차감)
  - DB 저장 실패 시 PG 승인 취소(보상 작업)
  - **완료 조건:** 정상 승인, PG 실패, DB 실패 후 보상 시나리오 테스트
  - **학습 포인트:** ARCHITECTURE 5-2(선 외부 I/O → 후 DB 트랜잭션). 왜 하나의 `@Transactional`에 PG 호출을 넣으면 안 되나?
  - **이후 변경 (phase-04 4-2+):** 이 명세는 Payment를 승인 **후에** 저장해, 결과를 모르는 상태와 실패 이력을 표현할 수 없었다. Payment를 PG 호출 **전에** `REQUESTED`로 생성하는 "결제 시도 기록"으로 재설계했다.

- [x] **3-4. 중복 결제 방지 (멱등성)**
  - `payment.order_id` UNIQUE 제약
  - `Idempotency-Key` 헤더 검증
  - 같은 주문에 대해 동시에 10번 승인 요청하는 동시성 테스트
  - **완료 조건:** 10번 중 정확히 1번만 성공, PG 승인도 1번만 호출됨
  - **학습 포인트:** DB UNIQUE 제약만으로는 왜 부족한가? (PG는 이미 두 번 호출됐을 수 있다 → 락 또는 상태 선점이 필요)
  - **이후 변경 (phase-04 4-2+):** 멱등키를 별도 테이블에서 `payment.idempotency_key` 컬럼으로 옮겼다.

- [x] **3-5. 결제 취소**
  - `PAID` 상태만 취소 가능, PG 취소 → Order `CANCELED`, 재고 복구
  - **완료 조건:** 취소 후 재고 복구 확인, 이미 취소된 주문 재취소 시 실패
  - **학습 포인트:** 결제 취소와 재고 차감이 동시에 일어나면?

- [x] **3-6. 결제 완료 이벤트**
  - 결제 완료 시 도메인 이벤트 발행, `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`로 후처리(알림 로그 등)
  - **완료 조건:** 결제 트랜잭션이 롤백되면 이벤트가 처리되지 않음을 테스트로 확인
  - **학습 포인트:** `@Async` 없이 AFTER_COMMIT 리스너에서 DB에 쓰면 왜 반영이 안 되나? (ARCHITECTURE 5-1)

**Phase 완료 후 스스로 답해볼 것**
- PG 승인은 성공했는데 우리 서버가 응답 직전에 죽었다. 사용자는 돈이 빠져나갔는데 주문은 `PENDING`이다. 어떻게 복구할 것인가? (→ Outbox, 결제 상태 대사(reconciliation)로 이어지는 주제)
